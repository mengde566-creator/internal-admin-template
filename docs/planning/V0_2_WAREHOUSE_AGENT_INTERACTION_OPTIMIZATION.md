# 0.2 仓储助手交互优化专项

> 状态：待研发实施
> 等级：L1（仓储助手单一交互链修复）
> 关联需求：`REQ-V02-AI-002`、`REQ-V02-AI-007`
> 关联功能：`FUN-02`、`FUN-07`
> 关联场景：`SCN-RP-04`、`SCN-RP-07`、`SCN-C-02～06`、`SCN-E-05`
> 目标：让“候选出现 → 用户选择 → 查询执行 → 成功或可恢复失败”成为稳定、可理解、可恢复的一条用户任务链

## 1. 本次只解决什么

用户面对多个候选物品时，应能直接选择一个物品并继续查询。选择、发送、失败、重试、刷新和切换对话都必须有明确状态，不能要求用户理解 `Task`、`revision`、`optionToken` 或内部 ID。

本专项不新增仓储 Tool，不调整模型、Prompt、Provider、Memory TTL、权限规则、数据库兼容策略，也不重新设计助手尺寸、布局或视觉主题。

## 2. 已确认问题与代码事实

1. `onDraftInput()` 在用户输入时静默清空 `pendingClarification`，用户不知道已经退出候选选择状态。
2. `sendMessage()` 在服务端确认接收前就清空候选，并先插入一条普通用户消息；网络或入口失败后，选择和重试上下文同时丢失。
3. 服务端候选令牌是一次性受信凭据，选择后 Task 从 `READY` 推进并清空候选；后续模型或 Tool 失败时，旧令牌不能再次使用。
4. 前端在 `run.failed` 后仍保留旧候选卡，用户可以再次点击已经失效的候选，只得到重复失败。
5. `chooseCandidate(candidate)` 没有接收所属卡片，而是从全部卡片中寻找第一个澄清卡；出现多个历史澄清卡时可能绑定错误的 `clarificationId`。
6. 候选按钮没有提交锁，快速点击可能产生重复操作。
7. 所有失败都显示“稍后再试”，没有告诉用户当前选择是否已被服务端接受、旧候选是否还能使用、下一步该重新选择还是重新查询。
8. 失败的乐观用户消息与成功消息外观相同，形成截图中的多条“选择物品……”记录，但没有对应的完整助手结果。
9. History 目前只恢复仍处于 `READY` 的候选；选择已被接受但后续失败时，没有可恢复的交互快照。
10. 现有测试集中在成功路径，未覆盖输入打断、双击、入口失败、接受后失败、旧卡失效、多卡绑定、刷新恢复和权限范围变化。

## 3. 用户交互合同

### 3.1 默认主路径

候选卡中的选项是明确动作。用户点击一个候选后，系统立即提交该选择，不再要求用户到通用输入框点击第二次“发送”。

```text
等待选择 READY
  → 已选择 SELECTED
  → 正在提交 SUBMITTING
  → 服务端已接受 ACCEPTED
  → 查询成功 SUCCESS
```

- 一次点击只创建一个 Run；提交期间所有候选按钮禁用。
- 卡片必须把自身 `clarificationId` 与被点击的 `optionToken` 一起提交，禁止从全局卡片中猜所属关系。
- 页面只展示业务名称、编码、单位和用户可理解的状态，不展示受信令牌、Task ID、revision 或内部数据库 ID。
- 成功后候选卡进入已完成状态，不能再次提交。

### 3.2 用户想改为自由提问

- 输入文字不得静默取消候选状态。
- 候选存在时，提供明确的“改为重新提问”或“取消本次选择”动作；用户确认后才退出候选链。
- 开始新话题、切换对话或权限范围变化时，按服务端事实清理当前交互，不在前端自行保留旧候选。

## 4. 失败与恢复合同

| 发生阶段 | 页面状态 | 用户可执行动作 |
| --- | --- | --- |
| 服务端尚未接受，HTTP/网络入口失败 | 回到 `READY`，保留原候选 | 重新点击同一候选 |
| 服务端已接受，模型/Tool/流式后续失败 | 旧候选标为失效，保留“已选择的物品”业务信息 | 使用服务端提供的受控“重新查询”动作；不得复用旧 token |
| 候选过期、revision 冲突或已被消费 | 禁用或移除旧候选并说明需要重新确认 | 重新发起原查询或重新获取候选 |
| 权限或部门范围变化 | 不透露旧对象是否仍存在，不恢复旧候选 | 按当前权限重新查询 |
| 用户取消或连接中断 | 显示唯一终态；不得产生第二次提交 | 根据服务端状态重新查询或继续新问题 |

错误文案必须说明“发生了什么”和“下一步做什么”，但不能暴露异常栈、错误 SQL、内部状态名或令牌。

## 5. 状态与事实源边界

- Conversation、Task 状态、候选是否有效、选择是否已经接受，均以后端为唯一事实源。
- 前端只维护当前交互投影和短暂的提交状态，不建立第二套 Task 状态机。
- 若现有 History DTO 无法区分 `READY` 与“已接受但可重新查询”，允许补充最小的受控交互快照；禁止建立候选表、事件溯源、通用工作流或新的聊天存储。
- 用户消息只有在服务端接受 Run 后才显示为正常提交；入口失败的乐观消息应移除或明确标记“未发送/未完成”，不得混入正常 History 外观。
- 重试必须创建新的 `clientRequestId`；旧 `optionToken` 是否可用只能由服务端决定。

## 6. 最小实施分块

### 开发块 A：先冻结状态回归

先增加不调用 Provider 的组件/服务测试，覆盖第 7 节场景。测试必须复现当前问题，不能只断言方法被调用。

### 开发块 B：前端交互收敛

- 候选点击改为携带所属卡片并立即提交；
- 增加一次提交锁和禁用态；
- 移除“选择后再点发送”的双步骤；
- 输入改为显式切换任务，而非静默清空；
- 根据确定性错误语义更新卡片、消息和可恢复动作；
- 失败操作不得伪装成正常完成的用户消息。

### 开发块 C：仅补必要后端差值

如果前端无法从现有 HTTP/SSE/History 合同确定“未接受、已接受、已失效、可重新查询”，只补最小 DTO、稳定错误码或恢复快照，并同步 OpenAPI 与生成类型。禁止借机扩展通用 Task 平台。

### 开发块 D：纵向验收

先用确定性 HTTP/SSE 测试完成候选、选择和失败恢复。全部门禁通过后，才允许一次正式 DeepSeek 调用验证“产生候选 → 点击候选 → 返回真实库存结果”；Qwen 调用为 0。只有定位到明确生产缺陷时才允许一次修正后复验。

## 7. 必须覆盖的验收场景

1. 单击候选立即提交，恰好一个 Run，不需要再点通用发送按钮。
2. 双击或快速连续点击只产生一个 Run。
3. 候选存在时输入文字不会静默清空；显式切换后才退出候选链。
4. HTTP 尚未接受即失败时，原候选仍可安全重试，不新增成功外观的用户消息。
5. 服务端已接受后模型/Tool失败时，旧候选不可再次提交，页面提供明确的重新查询动作。
6. 过期、重复消费、revision 冲突分别收敛为可理解状态，不循环显示通用失败。
7. 同一页面存在多个历史澄清卡时，点击选项始终提交所属卡片的 `clarificationId`。
8. 刷新或重新打开对话：`READY` 候选可恢复；已经接受的旧候选不恢复为可点击状态。
9. 切换 Conversation、新话题、权限或部门范围变化后，不携带旧选择。
10. 取消、SSE 中断和迟到事件不会产生第二终态、重复用户消息或重复 Tool。
11. 键盘和鼠标均可完成候选选择；提交中、失效和完成状态可感知。
12. 页面和 History 不显示 `optionToken`、Task ID、revision、内部数据库 ID 或技术错误。

## 8. 允许范围与禁止扩大

允许按最小连贯范围修改：

- `WarehouseAgentPanel.vue`、`agentApi.ts` 及现有相关测试；
- `module-agent` 中 Task 选择、Run/History 投影及相关 DTO、Service、Store、Controller 测试；
- 只有 HTTP 合同变化时同步 OpenAPI 和生成 TypeScript；
- 只有现有数据无法表达必要恢复状态且项目负责人确认时，才提出数据库变更，不得直接实施。

禁止修改：

- 仓储查询业务规则、Warehouse Mapper/表和仓储写操作；
- DeepSeek/Qwen 模型、Spring AI Tool loop、Prompt、Memory TTL 和观测架构；
- 助手尺寸、拖动、窗口布局、主题和其他仓储页面视觉；
- 通用工作流、消息队列、事件溯源、候选结果表或新状态管理框架；
- 无关模块、依赖版本、部署与运维脚本。

## 9. 完成门禁

- 状态场景测试先失败后通过，并覆盖第 7 节关键正常/失败路径；
- 前端定向测试、相关后端定向测试、typecheck 和受影响模块编译通过；
- 若 HTTP 合同变化，OpenAPI generate/check 无漂移；
- 一次真实浏览器走查覆盖选择、失败恢复、刷新和切换对话；
- 正式 Provider 调用遵守开发块 D 的有界预算；
- `git diff --check` 通过，差异不含禁止范围；
- 未执行项和剩余风险如实列出，不以“测试通过”代替交互结果。
