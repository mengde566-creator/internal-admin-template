# 0.2 仓储模块开发过程复盘与批量生产改进草案

> 状态：已确认（仅历史复盘，不作为实现依据）
> 日期：2026-08-19
> 性质：历史原因与改进建议，不是实现依据，不加入默认 AI 阅读清单
> 当前实现依据：根 `AGENTS.md`、已确认需求、模块 `CAPABILITY.md`、实际代码与测试

## 1. 结论

仓储模块最终形成了可运行、可验证的业务闭环，但开发过程尚未达到批量生产业务模块的效率要求。

```text
仓储工程结果：通过
模块边界验证：通过
批量生产方法：尚未通过
```

后续目标不是增加角色、报告和验收次数，而是把一次模块生产收敛为：**一次需求与交互确认、一个黄金纵切、一次同构扩展、一次源冻结验收**。

## 2. 已证明的能力

- 模块化单体、公开 API 和跨模块边界能够承载真实业务；
- Liquibase、OpenAPI、前端生成类型和模块测试可以组成自动闭环；
- 部门权限、四位小数、禁止负库存、幂等、CAS 和事务回滚已有机制证据；
- SQLite 默认路径与真实 PostgreSQL 迁移、精度、幂等和并发路径均得到验证；
- 仓储前端最终具备五个业务入口、动态多明细和响应式页面。

这些结果可以作为后续模块的工程参考，但仓储字段、规则和页面布局不能下沉为万能业务框架。

## 3. 主要过程问题

### 3.1 交付范围过大

最终提交包含118个文件、10781行新增和461行删除，同时混合IAM、仓储、前端、数据库运行和AI设计。该粒度不利于理解、回退和派生装配。

### 3.2 产品契约晚于生产实现

页面完成后才集中暴露“主数据”“No Data”、动态字段错位、重复位置来源和盘点表达不完整，说明用户术语、页面结构和状态契约没有在开发前形成可执行输入。

### 3.3 自动绿色不等于产品通过

组件测试、类型检查和构建可以通过，但无法自动证明动态表单在真实宽度下整齐、文案可理解、主题正确。早期走查偏向空数据和默认主题，真实业务数据进入太晚。

### 3.4 修正方式过于局部

同一页面出现结构问题后仍按单点补丁推进，导致多轮“最终修正”。第二次出现同类结构问题时，本应回到完整动作和状态矩阵一次复核。

### 3.5 状态和交接没有及时闭合

任务曾出现描述完成但没有实际进入目标对话，需求和架构中的“待建立”状态也没有随实现同步。任务状态必须以实际派发、代码和当前权威文档为准。

总设计阶段对上述问题负主要责任：架构和数据边界收敛较充分，但没有把用户语言、完整页面意图和真实走查条件作为研发输入。

## 4. 改进后的主路径

### 4.1 模块生产基线

开始开发前，只确认一份紧凑基线：使用者、用户术语、3—5条核心场景、数据关系、权限范围、页面入口、异常和非目标。

### 4.2 契约冻结

一次确定表结构、公开API、错误语义、页面字段和状态。实现中发现数据、权限或接口差值时先回到契约，禁止前后端分别增加临时解释。

### 4.3 黄金纵切

先实现一条同时经过数据库、Service、权限、OpenAPI、真实页面和错误状态的用户闭环。仓储如果重新开发，黄金纵切应为：

```text
创建物品 → 创建仓库与库位 → 两明细入库 → 查询库存 → 查看库存移动
```

纵切通过前不批量展开其余同类功能。

### 4.4 同构扩展

黄金纵切稳定后，由一个研发主责端到端扩展剩余场景，复用已经证明的分层、契约、页面状态和测试方式，不创建通用CRUD、表单DSL或单据引擎。

### 4.5 源冻结验收

早期只做一次真实主链探路；生产源码冻结后执行一次完整验证。UI使用真实业务状态，在需求确认的内容宽度和系统实际主题下检查动态布局，不用空数据截图或组件存在性替代。

## 5. 角色与提交边界

- 总设计师一次收敛需求、交互和公共边界；
- 一个研发工程师默认端到端负责生产实现、测试和真实页面走查；
- 运维只处理真实运行环境、部署配置和脚本；
- 独立审议只在重大方向、重复推翻或成本止损时介入；
- 多对话协作必须确认任务已经实际派发到唯一目标对话。

提交按可独立理解和回退的能力边界组织。需求、业务实现、前端实现、部署资产和后续AI设计不得仅因属于同一版本而混成一个大提交。

## 6. 成本与止损

每个模块只在最终交付中记录主责角色数、实现返工轮次、验证轮次和耗时，不建设仪表盘或新增报告体系。

出现同一页面或契约第三轮修正、验证超过计划两倍、治理文件多于产品与测试变更，或用户再次指出基础业务语言和布局缺失时，立即停止加码，重新收敛目标、最小范围、最近证据和延期内容。

## 7. 对AI阶段的验证

AI阶段使用一个真实黄金纵切检验本次改进：

```text
仓储用户登录
→ 打开轻量对话
→ 查询实时库存
→ DeepSeek调用一个仓储只读工具
→ SSE返回文本和固定库存卡片
→ 复制或打开人工页面
→ History、Memory和Observation形成唯一终态
```

先证明Session、部门权限、流式、工具、卡片、History和观测链，再增加带引用的模拟知识问答；不先分别铺完Agent、Knowledge和Observability的全部能力。

## 8. 审核后落点

本次只向现有唯一事实源补充最小差值：

- 需求模板补用户术语、权限数据、黄金纵切和页面状态；
- 能力包模板指向已确认需求、页面状态契约和黄金纵切；
- 工程用户走查增加真实业务状态、目标宽度和实际主题；
- 已存在于交付协议和根规范的规则不再复制；
- 第三个真实业务模块完成前不建设万能模块生成器。

本复盘保留历史解释作用，不成为新的流程规则源。
