## 1. 需求漏斗（0.1 闭环的再结构化）

0.1 的唯一业务闭环：

```text
内部人员统一登录 → 进入工作台/内容管理 → 编辑公开主页内容 → 上传展示图片
→ 保存草稿 → 预览 → 发布 → 外部访问者查看已发布主页
→ 修改草稿不影响线上内容 → 撤回后停止公开
```

按模式结构化（意图 → 功能清单 → 非目标）：

- **意图**：验证一条"登录—内容管理—草稿—发布—匿名查看—撤回"的完整闭环，同时验证 AI 功能产出流水线；
- **功能清单**：管理员初始化与统一登录、最小工作台、主页编辑（含两套代码定义配色）、图片上传、草稿保存与预览、发布与撤回、最小审计；
- **非目标**（防许愿式编程的边界）：不建部门管理、岗位、数据范围、动态菜单、配置、字典、主题表、历史版本、审计查询平台、外部客户、Python/AI 模块、微服务。

## 2. 实体关系认识（表结构的依据）

按模式 11.7："数据结构认识要上升到实体关系级别，表结构是实体关系认识的落地结果。"

### 2.1 实体清单（9 个实体 = 9 张表）

| # | 实体 | 业务含义 | 关键属性 | 0.1 边界（不建什么） |
| --- | --- | --- | --- | --- |
| 1 | 部门 | 组织归属，0.1 只有根部门 | id、code(唯一)、name | 无 parent_id/负责人/排序 |
| 2 | 用户 | 内部人员（管理员/普通用户/发布人员都是用户+角色） | id、department_id、username(唯一)、display_name、password_hash | 无手机/邮箱/状态/头像 |
| 3 | 角色 | 权限的载体，预置"系统管理员" | id、code(唯一)、name | 无继承/数据范围 |
| 4 | 用户-角色 | 用户与角色的多对多关联 | user_id+role_id(联合主键) | — |
| 5 | 角色-权限 | 角色关联权限编码 | role_id+permission_code(联合主键) | 不建权限点表（权限由代码注册） |
| 6 | 文件 | 本地展示图片的元数据 | id、relative_path(唯一)、content_type | 无上传者/文件名/大小/缩略图 |
| 7 | 主页草稿 | 当前可编辑的草稿（单例） | id(固定1)、site_name、introduction、hero_file_id、contact_text、color_scheme | 无历史/多模板 |
| 8 | 主页发布 | 当前公开快照（单例），与草稿隔离 | 同上 + visible、published_by、published_at | 无历史版本 |
| 9 | 操作审计 | 发布/撤回结果记录 | id、operator_id、action、target_id、result、occurred_at | 无旧值/新值/JSON 详情 |

### 2.2 关系

```text
部门 ──1:N── 用户 ──N:N── 角色 ──N:N── 权限编码（代码注册）
用户 ──（只存标识）── 操作审计.operator_id
文件 ──被引用── 主页草稿.hero_file_id
文件 ──被引用── 主页发布.hero_file_id
主页草稿 ──发布时复制──▶ 主页发布
主页发布 ──产生──▶ 操作审计
```

跨模块只存对方标识，不建跨模块外键（`hero_file_id`、`operator_id`）——与模块边界规则一致。

## 3. 规则材料（影响面硬规则初稿）

按模式 11.5（模板预置硬规则 + 用户按系统补充），0.1 可预置：

- **表结构变更 = 较大改动**（删列/改类型/加非空/动索引）；
- **权限模型变更 = 较大改动**（角色/权限编码/越权判定）；
- **公共 API 签名变更 = 较大改动**；
- **主页发布表（site_homepage_publication）是公开契约**——改动必须保证"失败时旧快照继续有效"，不允许半发布状态（来自 REQ-V01-008）。

## 4. 表结构方案审视（模式原则 × 9 张表）

| 模式原则 | 方案是否满足 | 说明 |
| --- | --- | --- |
| 每张表对应一个实体 | ✅ | 9 实体 = 9 表，无冗余表 |
| 只实现明确需求 | ✅ | 无启停状态、权限表、主题表、历史表、Session 表 |
| 表结构是实体关系的落地 | ✅ | 字段全部来自实体关键属性，无发明字段 |
| 跨模块只存标识 | ✅ | hero_file_id、operator_id 不建外键 |
| 单例约束 | ✅ | 主页两表用 `CHECK (id = 1)` 保证最多一行 |
| 草稿与发布隔离 | ✅ | 两个实体分开存储；**为什么不是一张表+状态列**：草稿修改不影响线上要求两份独立数据，发布是快照复制，一张表无法同时表达"编辑中"与"已公开"两份内容 |
| 撤回语义 | ✅ | 撤回只置 visible=false，保留快照、草稿不受影响——符合 REQ-V01-008 |
| 配色编码 | ✅ | 只存 `GRAPHITE`/`AZURE` 稳定编码，不建主题表——符合 REQ-V01-005 非目标 |

**走查结论：9 张表方案在模式框架下成立，建议确认。**

## 6. 已确认的待细化项（2026-08-03）

### 6.1 图片上传规则（已确认）

- **存储位置**：项目本地持久化目录 `data/uploads/`，数据库只存相对路径（`file_asset.relative_path`）；
- **允许类型**：白名单 `jpg` / `jpeg` / `png` / `webp`，其余明确拒绝；
- **大小限制**：≤ 10MB（2026-08-03 由 ≤5MB 调整）；
- **文件命名**：系统生成（时间戳/UUID），规范化相对路径，**禁止用户输入路径**；
- **访问规则**：受控接口读取——公开接口读取文件时校验该文件是否被"当前可见的发布快照"（`site_homepage_publication` 且 `visible=true`）引用；未发布草稿引用的图片，公开接口读不到；
- **失败行为**：类型/大小/存储失败明确拒绝，失败时不留下半公开文件。

### 6.2 管理员初始化方式（已确认：默认账号 + 强制改密）

- 启动时若无任何用户，创建预置管理员账号（如 `admin`）；
- **初始密码不写死明文**：随机生成，首次启动输出到日志/控制台（开发者零配置即可拿到）；
- **首次登录强制修改密码**：改密前不能访问其他功能；改密后按正常流程使用；
- **强制改密适用于所有用户**（2026-08-03 确认）：管理员创建的用户首次登录同样强制改密（初始密码由管理员设置，用户登录后改密拥有自己的密码）；
- 不通过 Liquibase 写入固定明文凭据（符合表结构方案第 8 节）；
- 密码使用可靠哈希存储（AGENTS.md 安全要求）。
