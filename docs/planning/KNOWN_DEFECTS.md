# 已知缺陷台账

> 状态：生效
> 版本：1.0
> 日期：2026-09-21
> 用途：登记**已复现的产品缺陷**、原因、影响、状态与关闭证据，供修复排序和事后复盘
> 关联：[`USER_SCENARIO_TEST_SYSTEM.md`](USER_SCENARIO_TEST_SYSTEM.md)（场景测试与登记机制）、[`../HANDOFF_CURRENT_PROJECT.md`](../HANDOFF_CURRENT_PROJECT.md)（当前事实入口）

## 1. 定位与边界

- 本台账只回答两件事：**现在有哪些已知未修缺陷**、**每个缺陷是什么原因导致的**；
- **修复机制不在这里**：修复由场景测试驱动——失败问法 → 按最小连贯改动修 → 场景转绿 → `FIXED?` → 关闭登记；
- **只记产品缺陷**。测试、脚本、工具自身的错误不进台账（它们在场景方案的试点记录与提交说明里）；
- 台账不复制复现内容：复现、期望、观测证据的**唯一事实源是场景资源文件**，台账只引用并记录状态与原因。

## 2. 规则

1. **没有可执行的失败复现，不许进台账**。复现可以是**场景用例**（能通过正式入口跑出来，登记 `caseId` + 问法）或**单元用例**（代码级回归，且必须真的先红后绿）；两者都没有的，只写在"待登记"清单里。属于场景用例时，登记时给场景资源的 `knownDefects` / `knownUnstable` 补上 `defectId`，形成双向绑定。
2. **发现即登记，登记不等于排期**。任何执行者（含 AI）发现即可登记，状态先写"待决策"；修不修、什么时候修由项目负责人决定。
3. **每条必须写原因**，并区分：
   - `已证实`：有 runId、日志、代码位置支撑；
   - `推断`：只到现象与机制假设，需研发确认。
4. **关闭是机械的**：场景转绿 → 资源里出现 `FIXED?` → 删除该条登记、台账状态改"已关闭"，并写入验证用的 `runId`。不开验收会、不写单独报告。
5. **复发升级**（项目负责人 2026-09-21 确认）：

   | 复发情况 | 触发动作 |
   | --- | --- |
   | 第 1 次 | 登记 + 最小连贯修复 |
   | **同一缺陷在 ≥2 个批次或版本再次出现** | 按 `AGENTS.md` 红线 16.2 第 5 条：**停止本地修补**，先检索同类成熟项目与权威方案，形成完整方案后再动手 |
   | **跨 ≥2 个版本仍存在，或同一根因产出 ≥3 条缺陷** | 触发独立项目审议与成本止损复核（`AGENTS.md` §0.3、版本交付协议 §2.1） |

6. **不新建的东西**：不做缺陷审批、不做每缺陷报告、不做独立跟踪系统、不做优先级评审会、不给每个缺陷建任务书。
7. **提风险必须同时给建议**（项目负责人 2026-09-21 明确要求）：提出任何隐患、退化风险或结构性担忧时，**必须在同一条里给出建议**——含"建议怎么做、代价多大、不做的后果"。禁止只报问题不给路径，禁止把建议推迟到"后续再讨论"。

## 4. 缺陷详情

### DEF-001 碎句问法整轮失败

- **复现**：`module-agent-warehouse-adapter/src/main/resources/evaluation/warehouse/warehouse-stock-query-scenario-v1.json`，`caseId=stock-query-01`，问法 `{itemCode}，现在，多少`
- **证据**：`runId=c214d5c3-afe7-4fd7-8787-dbcbfffe2a8b`；SSE 终态 `run.failed {"code":"AI_PARAMETER_INVALID","retryAvailable":false}`；助手回复"助手请求参数不合法"；History 终态 `FAILED`；服务端日志 `agent_tool_call stage=callback result=failed code=AI_PARAMETER_INVALID` → `stage=guard result=rejected code=AI_BUSINESS_REJECTED` → `agent_model_failure_unknown stage=STREAM`
- **补充观测**：修复 `DEF-002` 后复跑，同一问法（`runId=ec72cc12-a003-4efc-b8f8-6a1169e4b003`）的助手回复显示为**原始错误码 `AI_PARAMETER_INVALID`**。即同一缺陷的用户可见文案在两轮之间不一致：有时是自然语句，有时直接暴露内部错误码——关闭时必须同时固定文案来源。
- **原因（已证实）**：碎句下模型未把编码填入 `itemMentions`；仓储 Tool 的"明确编码不得省略"守卫（`WarehouseInventoryToolProvider#requireExplicitItemMention`）按设计拒绝；模型随后重试同一工具，被"前序失败闭锁"拒绝；异常冒泡到流式阶段，整轮以失败结束。
- **缺陷点**：守卫的意图正确（防止退化成全库存概览），**错在失败语义**——它把"模型漏填参数"表达成整轮失败，而不是受控的业务拒绝或澄清。
- **影响**：合法问法被系统归因为"参数不合法"，用户得不到任何结果；同一问法多次复现以失败为主。
- **关闭条件**：该问法在场景中稳定得到 `ANSWERED`，或得到受控的业务拒绝/澄清，且 Run 不再硬失败。
- **修复与关闭（2026-09-21）**：
  - 修复方式：守卫由"抛错终止整轮"改为"**从用户正文补齐模型遗漏的明确编码**"——`WarehouseInventoryToolProvider#requireExplicitItemMention` 现在返回可用线索，并从**原始正文**提取以保留编码大小写；判据（存在明确编码引用）与归一化方式保持不变。
  - 单元回归：原用例 `omittedExplicitBusinessCodeCannotBroadenStockToOverview` 改写为 `omittedExplicitBusinessCodeIsRecoveredFromTheUserMessageWithoutBroadeningStock`，新增断言"必须用正文编码查询"且"**绝不允许退化为空线索的全库存概览**"；该模块 `37/37` 通过。
  - 关闭验证：场景中该问法由 `KNOWN-DEFECT` 转为 `PASS`（`runId=c9749eae-e648-4b07-bd48-ebe16a475687`），随后移除登记复跑，整份场景 `9/9` 通过、失败 0。
  - **遗留观察（未登记）**：该失败路径不再触发，因此"把原始错误码当作助手文案展示"的现象在本缺陷内消失；**其他失败路径是否也会这样展示尚未排查**。按台账规则，没有复现用例就不能登记——一旦复现即补 `caseId` 后登记为新缺陷。

### DEF-002 纯乱码仍查询并返回库存概览

- **复现**：同上资源，`caseId=garbled-input-01`，问法 `￥%……&*（）——+`、`asdkjfhalksdjf ？？？ zxcvbnm`
- **证据**：`runId=ac3b9774-058a-49b9-adfd-775e0cd0ac05`（`conversationId=810c13af-c99f-418b-9761-f70415559ba6`）、`runId=8814bc4f-8e8b-4cfe-b600-ee036b901456`（`conversationId=16c0126d-e665-43c3-b5df-99fc685dbf4a`）；两条均由 History 取回：`cardType=stock-summary`、`status=STOCK_RESULT`、`outcome=ANSWERED`、`resultCount=5` 与 `10`、`truncated=true`，`rows` 为真实库存明细（物品编码、仓库、库位、数量）；助手回复"尚未指定具体对象，所以先展示部分库存方便继续选择：…"
- **原因（已证实）**：入口没有"输入是否可理解"的判断，纯乱码直接进入工具选择；工具在**空物品线索**时走的是"返回有界库存概览 + 提示继续选择"分支（该分支本身是为了服务"含糊但有效的问法"），于是乱码输入也拿到了授权范围内的库存概览，并被标记为 `ANSWERED`。
- **缺陷点**：同一个"空线索"分支同时服务两类输入——**"有效但含糊"（应给概览并澄清）与"完全不可理解"（不应查询）**，当前实现无法区分二者。
- **影响**：违反 `SCN-I-03`"不查业务数据"；随机或无意输入即可批量取得当前账号授权范围内的库存明细（`SCN-AU-06` 枚举探测同类风险）；概览以正常回答呈现，用户与审计都无法察觉这次查询没有业务意图。
- **关闭条件**：不可理解的输入稳定不调用任何业务工具、不出现业务卡片，直接说明没有理解并请用户补充；同时"含糊但有效"的问法仍能正常得到概览与澄清。
- **修复与关闭（2026-09-21）**：
  - 修复方式：在编排层增加入口门禁——用户消息不含任何可识别线索（无汉字、且无"字母数字混合或含分隔符"的类编码词元）时，**不进入模型与工具链**，直接给出受控的补充提示并正常结束本 Run；判据与实现见 `AgentConversationService#hasServiceableClue` 与 `#completeUnintelligibleInput`。
  - 关闭验证：同一条问法在场景中由 `UNSTABLE-FAIL` 转为 `PASS`；服务端日志两次出现 `event=agent_input_unintelligible stage=terminal result=success ... tool=none code=SUCCESS`（`runId=413287e6-03d4-40fc-99b2-29713e846b40`、`runId=4b25994b-d334-43ff-a3eb-a9dac651fd82`），两次相隔 45 毫秒；同窗口模型请求为 7 次（9 条问法减去被门禁拦下的 2 条），证明这 2 条没有调用模型、更没有调用业务工具。
  - 登记已从场景资源中移除；移除后这两条问法以普通 `PASS` 参与回归。
  - **已知限制**：判据只认汉字与类编码词元，纯英文且不含数字与分隔符的问题会被判为无线索（用户会收到"请补充"提示）。如需支持多语言线索，应改为由业务适配器各自声明线索规则。

### DEF-003 错别字问法的澄清候选不稳定

- **复现**：同上资源，`caseId=clarify-typo-01`，问法 `{itemName} 还有多勺子`
- **证据**：首次失败时报告给出实际候选；复验通过时候选为 `{code=SCNPILOT-…, name=场景试点轴承…, mention=轴承…, resolved=true}` 与 `{code=勺子, resolved=false}`
- **原因（已证实）**：模型把错别字片段也抽取为一个物品提及（`pendingMentions` 含多项），澄清候选按提及逐个解析生成；正确物品是否出现在候选里取决于该轮抽取结果，因此时好时坏。**澄清本身是被允许的结果**，不稳定的是候选质量。
- **影响**：用户说全了物品名称却需要挑选，且有时挑不到正确项。
- **关闭条件**：该问法每次澄清都给出包含正确物品的受信候选；或稳定直接作答。

### DEF-004 排除型问法把被排除的物品当成正向线索（同日发现并修复）

- **复现**：单元用例 `WarehouseInventoryToolProviderTest#excludedItemCodeIsNeverInjectedAsAPositiveClue`（修复前**确实红**：缺少正向线索时既未受控拒绝、也发生了业务查询）
- **原因（已证实）**：`DEF-001` 的补齐在 `excludedItemMentions` 非空时同样生效，绕过 `bindExcludedMentions` 的"空正向线索 → 受控拒绝"守卫；排除型问法里最像编码的词元正是**被排除的那个**，于是被注入成正向线索。
- **影响**：用户问"除了 X 以外还有哪些库存"时，系统可能**去查 X**——静默错答，而旧路径是受控拒绝。
- **修复与关闭（2026-09-21）**：补齐仅在 `excludedItemMentions` 为空时生效；新增上述单元用例并纳入回归。`WarehouseInventoryToolProviderTest` **40/40 通过**；整轮场景 **10/10 通过**（`runId` 见第 6 节变更记录）。
- **遗留**：本缺陷只有单元级复现（排除型问法不是已确认用户场景，见 3.1）。

### DEF-005 知识检索测试类在已提交边界上失败（判定为测试过期，已关闭）

### DEF-006 模块边界检查在缺少 `rg` 时静默通过（同日发现并修复）

- **复现（修复前）**：`bash scripts/check-module-boundaries.sh` → 打印"模块边界检查通过（仅生产源码）"、**退出码 0**；同一时刻 stderr 出现 `line 17/25/33: rg: command not found`。`command -v rg` 无输出，`/opt/homebrew/bin/rg`、`/usr/local/bin/rg` 均不存在。
- **原因（已证实）**：三处检索都写成 `done < <(rg ... || true)`。`rg` 不存在时命令以 127 失败并被 `|| true` 吞掉，`while` 读不到任何行，`FAILURES` 保持 0。`rg` 也没有列入 `quality.sh` 的 `check_prerequisites`，项目文档只把它当便利工具提及——**依赖未声明，缺失时无人能发现**。
- **影响**：门禁第 1/9 步长期空转。`module-file`/`module-audit`/`module-iam` 禁止跨业务模块依赖、权限命名空间前缀、`frontend/src/shared` 禁止导入业务模块——这三条架构红线没有任何自动看守，而每次门禁都会打印"通过"。与 `DEF-005`/R3 同属"门禁静默变绿"，但这条更严重：`DEF-005` 至少红过，这条从未真正运行过。
- **修复（2026-09-21，采用建议中的方案 A）**：三处检索改为 POSIX `find` + `grep -HnE`（原 glob 语义用 find 的 `-name`/`-path` 谓词表达；权限命名空间那处的 PCRE `\K` 改写为"匹配到冒号 + 从最后一个引号切分"）。同时脚本开头校验 `dirname/find/grep/sed` 是否存在，缺失立即失败——把根因（工具缺失无人检查）一起堵掉，并去掉未声明依赖：不再需要 ripgrep。
- **三条证明（全部实跑）**：
  1. **红灯**：同时植入三类真实违规（`module-file` 导入 `module-iam`、`hasAuthority("secret:read")`、`frontend/src/shared` 导入 `@/modules/warehouse/...`）→ 脚本**恰好报出 3 条违规、退出码 1**；
  2. **绿灯**：删除探针后 → "模块边界检查通过（仅生产源码）"、**退出码 0**（说明现有代码库确实合规，不是靠放宽规则变绿）；
  3. **工具缺失**：以空 `PATH` 运行 → 一条明确错误、**退出码 1**（不再静默通过）。
  - 接线复核：`./scripts/quality.sh --no-database` 第 1/9 步现在是真的在检查，整层退出码 0。
- **修复过程中被红灯抓到的问题（复盘要点）**：重写初版漏了 `grep -o`，权限命名空间按整行切分，把正常的 `@PreAuthorize("hasAuthority('file:manage')")` 误报成违规。**只做绿灯验证不会发现这个假阳性**——它会让门禁对合法代码变红。教训已写入第 5 节。
- **当时评估的另一个方案（未采用）**：保留 `rg`，改在 `check_prerequisites` 与脚本内声明并安装 ripgrep（3 行）。未采用的原因：它把"检查是死的"换成"每个新环境都必须先装 ripgrep"，代价落在每台机器上，而这台机器当时就没有 `rg`；而这三处检索并不需要 PCRE。

## 5. 复盘用法

- **按根因归类看模式**：同类根因（如"失败语义"）出现多条时，问题通常不在单点，而在该层缺少统一约定；`DEF-001` 与 `DEF-004` 就是同一天同一层的两个实例。
- **按复发次数触发升级**：复发次数由"同一现象在不同批次或版本再次被观察到"累加，达到阈值即按第 2 节第 5 条升级，**不靠记忆判断**；
- **关闭证据留在台账**：每条关闭必须带验证 `runId`，便于日后核对当时的构建与结论。
- **重写检索/门禁类检查必须双向验证**（`DEF-006` 修复时踩到）：只做绿灯会漏掉**假阳性**（初版漏 `grep -o`，把合法的 `hasAuthority('file:manage')` 误报成违规，会让门禁对正确代码变红）；只做红灯会漏掉**假阴性**（检查看着能抓违规，其实根本没运行）。两边都要有可复跑的证据，且探针必须用**真实调用形式**——`DEF-006` 第一次探针把权限写成 `check("secret:read")`，那不是一个能被任何实现抓到的违规，等于没证明。
