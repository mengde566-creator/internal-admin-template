# 管理端页面美观与友好度优化专项（实施与验收对照）

> 状态：**已完成第二轮缺口收敛与闭环，真实页面走查已完成，待项目负责人最终验收**
> 范围：管理端公共外壳、IAM 页面、仓储页面、AI 观测、知识资料及跨页面错误反馈
> 已确认边界：**本专项只修改前端，重点为样式、交互、提示与系统友好度；不修改后端或接口契约**
> 形成日期：2026-09-03
> 证据位置：工作区目录 `docs/planning/evidence/admin-ui-usability/`（包含 16 条路由 × 4 视口的 mock API 浏览器视觉扫描度量与 64 张截图；不证明真实后端用户链）

## 1. 核心判断

当前问题不是单一颜色或圆角不好看，而是页面信息架构、首屏密度、操作层级和错误反馈没有形成统一规则：

1. 仓储页面同时堆叠顶部栏、领域标题、领域说明、二级导航、子页标题和子页说明，重复介绍挤占首屏，用户需要滚动后才能看到主要业务数据；
2. IAM、仓储、AI、知识页面各自维护一套页面头、筛选区、内容容器和空态样式，视觉密度与空间使用明显不一致；
3. 原生文件选择控件直接暴露浏览器默认样式，与现有 Element Plus 控件不一致，也缺少清晰的选中文件、替换、清除和限制反馈；
4. 部门树没有足够的容器、行高、层级引导和操作分区，节点文字、状态与操作挤在同一行；
5. 错误反馈大多只透传一句后端 `message`，没有说明“哪个任务失败、影响什么、问题位置、如何恢复”，技术术语直接暴露给业务用户；
6. 现有专项已经解决滚动链、固定列遮挡、长字段可读性和 Agent 尺寸等问题，本专项不重复推翻这些成果，只补齐当前仍未解决的首屏结构、跨页面一致性和反馈语义。

## 2. 设计意图

专项采用“业务信息优先的紧凑管理台”方向：

- 用户进入页面后，首屏先看到筛选、主要操作、数据概况和至少一部分真实业务数据；
- 页面说明只保留完成任务所需的一句话，低频规则进入帮助提示、就近说明或可展开区域；
- 主操作、次操作、危险操作和帮助信息形成清晰层级；
- 同类页面共享视觉规则，但不新建重型页面框架或第二套主题系统；
- 继续使用 `frontend/src/shared/styles/tokens.css` 作为唯一颜色与视觉令牌来源；
- 美观必须服务于信息识别、操作效率和错误恢复，不做纯装饰性改版。
- 所有改进必须在现有前端数据和接口合同内完成；前端没有收到的位置或原因不得猜测、伪造，也不得借本专项要求后端扩展返回字段。

## 3. 全系统扫描与同类问题一次收敛

### 3.1 本专项不是截图点修

项目负责人指出一处问题时，该处只作为**同类缺陷的扫描入口**，不能只修截图对应页面。专项正式实施前必须先完成一次全系统基线扫描；每批研发完成后还必须围绕实际根因反查全部同源消费者。

例如发现“节点文字与操作堆叠”后，不能只调整当前部门节点，必须同时检查：

- 所有树、嵌套列表、表格操作列、状态标签与行内按钮组合；
- 相同 CSS 类、共享组件、Element Plus 插槽写法及复制出来的局部样式；
- 默认数据、长名称、多角色标签、多按钮、三级层级、窄窗口和 125% 缩放；
- 弹窗、抽屉、折叠区和异步加载完成后的同类布局。

只有扫描范围内的同类实现均得到“有问题已纳入、无问题有证据、不适用有理由”之一的结论，该问题才允许关闭。禁止再次采用“用户指出一处、研发只改一处”的点状交付方式。

### 3.2 路由覆盖范围

扫描基线以当前路由注册表为准，覆盖全部 16 条用户页面，而不是只覆盖本次截图；本轮扫描器通过 mock API 提供页面数据，仅用于浏览器视觉覆盖，不证明真实后端用户链：

- 登录与改密：`/login`、`/change-password`；
- 工作台与主页内容：`/`、`/site`；
- IAM：`/users`、`/departments`、`/roles`；
- 系统配置：`/system-config`；
- 仓储五条子路由：`/warehouse/stock`、`/warehouse/operations`、`/warehouse/items`、`/warehouse/locations`、`/warehouse/records`；
- AI 与知识：`/ai-observability`、`/ai-knowledge/drafts`；
- 公共展示页：`/public`。

权限导致不可见的页面或状态必须使用职责匹配的真实账号补查；若当前环境确实无法到达，必须明确记录为未覆盖项，不能默认视为无问题。新增路由在专项关闭前也必须补入清单。

### 3.3 每页统一扫描维度

每个路由至少检查下列维度，并记录页面级结论：

1. **首屏任务密度**：标题、介绍、导航是否重复，核心筛选、主操作、表头和业务数据是否被推到首屏之外；
2. **布局碰撞**：文字叠压、按钮挤压、操作列截断、浮层遮挡、容器溢出、非预期横向滚动；
3. **信息层级**：标题、说明、状态、主要/次要/危险操作和空态是否容易区分；
4. **控件一致性**：搜索、筛选、分页、文件选择、日期、树节点、表格操作、弹窗和抽屉是否遵循同一交互规则；
5. **内容压力**：长中文、长编码、多角色/多标签、多行错误、三级树、满页数据和空数据；
6. **过程状态**：初始、加载、成功、空数据、无权限、校验失败、系统异常、重试及部分成功；
7. **错误可恢复性**：任务、影响、位置、原因、下一步和安全追踪标识是否齐全；
8. **响应式与缩放**：1440×900、1280×720、1024×768、390×844，以及桌面端 100%/125% 缩放；
9. **可访问性**：键盘顺序、焦点可见、标签/名称、颜色对比，以及不依赖 hover 才能完成操作；
10. **主题与浮层**：默认主题并抽查 Ocean/Midnight，验证对话框、下拉框、抽屉、消息提示和仓储助手入口。

### 3.4 代码侧同源反查

浏览器扫描之外，研发前必须进行一次代码侧模式盘点，至少覆盖：

- 路由页面、公共布局、`tokens.css` 和实际生效的全局样式；
- 重复定义的页面头、工具栏、筛选区、内容容器、树节点、表格操作和错误横幅；
- 原生表单控件与 Element Plus 控件混用；
- 固定高度、绝对定位、`white-space`、`overflow`、`flex-shrink`、小行高及缺少最小宽度等高风险布局写法；
- 未定义令牌、局部硬编码颜色/间距，以及同一语义存在多套实现；
- 同一个共享组件、CSS 类或复制模板的全部消费者。

代码扫描用于识别根因与传播范围，不能代替真实浏览器走查；浏览器截图也不能代替消费者反查。

### 3.5 扫描产物与关闭门槛

修改页面前先形成一份可复核的问题台账，至少包含：路由/组件、真实用户任务、复现条件、问题截图、严重度、疑似同源实现、拟处理批次和不处理理由。相同根因的问题合并为一个问题族，避免逐页重复派单。

每个问题族关闭时必须具备：

- 根因及全部已知消费者清单；
- 受影响路由的同尺寸修改前/后证据；
- 长内容、满数据、空数据、失败状态和规定视口中的代表性验证；
- 未修改消费者的“确认无问题”或“不适用”结论；
- 一条能够防止该问题族再次出现的最近测试、共享规则或明确代码约束。

若同一类问题在专项期间第二次被项目负责人从遗漏页面指出，立即暂停该问题族的继续点修，重新检查扫描方法和根因归类；不得继续追加第三个局部补丁。

## 4. 当前已确认问题清单

以下是当前截图与代码已经确认的首批问题，不代表全系统问题总表；完整台账必须由第 3 节的扫描补齐后，才能开始批量修改。

### P0-1 首屏被重复标题和介绍占用

**真实表现**

- `/warehouse/items`、`/warehouse/records` 在 1304×768 左右窗口中，顶部栏之后再次展示“仓储管理 / 仓储 / 领域说明 / 五项导航”，子页又展示“物品档案 / 物品 / 说明”或“追溯库存变化 / 库存记录 / 说明”；
- 物品导入区和数据表、库存记录筛选区和表格被推到首屏下半部，表格只露出少量行；
- 顶部栏还显示当前子页名称，形成三层标题语义重复。

**代码事实**

- `WarehouseManagePage.vue` 固定渲染领域标题、说明和二级导航；
- 五个仓储子页分别再次渲染 `view-heading`；
- `AppTopbar.vue` 固定占用 `68px`，仓储外壳另有上下 `24px` 内边距及两处 `16px` 间距。

**目标规则**

- 仓储领域页头与当前子页标题合并为一个紧凑头部；
- 二级导航保留，但与标题同行或紧邻，避免独占一个大区块；
- 通用领域介绍默认压缩为单行辅助信息；只有首次理解或高风险操作需要的规则放在就近提示中；
- 1280×720、左导航展开时，无需页面滚动即可看到主要筛选/导入操作、表头和至少 3 行业务数据（数据足够时）。

### P0-2 部门树缺少可读的节点布局

**真实表现**

- `/departments` 的树直接落在白色背景上，没有内容卡片边界、节点分隔或稳定内边距；
- 根节点与子节点的名称、编码、状态、多个文字按钮挤在一条较矮的行内；
- 层级关系主要依赖很小的展开箭头和默认缩进，扫描困难；长名称、125% 缩放或更多层级时更容易拥挤、换行或叠压；
- “新建下级、编辑、停用、删除”同时常驻，危险操作层级过强。

**代码事实**

- `DepartmentManagePage.vue` 的 `.tree-node` 只有 `display:flex`、`gap:.5rem`，没有最小行高、内边距、分隔、换行和操作收敛规则；
- `<el-tree>` 外没有内容容器样式。

**目标规则**

- 树放入明确的业务内容容器，节点最小高度、上下间距、悬停态和选中态统一；
- 名称为主信息、编码为次信息，状态与操作形成独立区域；
- 层级通过缩进和连续引导线表达，不仅依赖箭头；
- 常用操作直接可达，低频/危险操作收入口或二次菜单；
- 100% 与 125% 缩放、长名称和至少三级树下不得文字叠压，键盘焦点清晰。

### P0-3 文件选择控件与任务流程割裂

**真实表现**

- 物品导入和知识资料页面直接显示浏览器原生“选择文件”控件，外观、尺寸、焦点态和按钮体系与页面其他控件不同；
- 文件名与“上传并分析”之间缺少完整的选择状态、替换、清除和约束反馈；
- 错误发生后，用户不容易判断文件是否仍被选中、是否应替换文件或能否直接重试。

**代码事实**

- `WarehouseItemsPage.vue` 与 `KnowledgeDraftManagePage.vue` 均直接使用 `<input type="file">`；
- 两页分别维护文件名/提示，尚未形成一致交互。

**目标规则**

- 使用现有 Element Plus 能力或小型项目内文件选择外观，不引入新依赖；
- 未选择、已选择、上传中、校验失败、可重试五种状态必须可区分；
- 明确显示文件名、类型/大小限制，并提供“选择/替换”和“清除”；
- 文件错误出现时，提示与当前文件卡片就近关联；
- 键盘可操作，文件名过长时全文可达。

### P0-4 错误提示缺少业务语义、位置和恢复动作

**真实表现**

- 本次物品模板上传只显示“不支持外部关系”；用户不知道“关系”是什么、在哪个文件或工作表、为何会阻止导入、下一步该怎么做；
- 页面错误通常只是一条红色横幅或消息气泡，标题、原因、影响和动作没有分层；
- “系统内部错误”与可预期的文件校验拒绝容易混淆。

**代码事实**

- `messageOf()` 和 IAM 页面 `errorMessage()` 仅返回 `response.data.message`；
- 统一响应已有稳定 `code` 和 `message`，但前端没有按任务语义映射；
- 全局异常边界会把未预期异常统一为“系统内部错误”，这是必要的安全边界，但页面缺少可恢复动作和问题追踪信息。

**目标规则**

错误块至少回答：

1. **发生了什么**：例如“文件无法分析”，而不是只显示技术原因；
2. **影响什么**：例如“尚未写入任何物品数据”；
3. **问题在哪里**：优先使用现有响应或页面上下文中已经具备的文件名、工作表、源行/字段；无法精确定位时明确写“文件级问题”或“暂时无法定位具体位置”，不能伪造不存在的行号；
4. **为什么**：将“外部关系”等术语翻译为业务语言，例如“文件包含指向其他工作簿或网络地址的链接”；
5. **下一步怎么做**：替换文件、修改第 N 行、刷新事实、重新预览或联系管理员；
6. **如何追踪**：未预期异常只展示安全的错误码/请求标识，不暴露堆栈、SQL、服务器路径或包内 XML 路径。

本专项固定保持现有 `ApiResponse` 和全部业务接口不变：对稳定错误码、已有消息和页面上下文做前端任务化表达，物品预览继续使用已有源行信息。若扫描发现现有接口无法提供用户所需的精确位置，只记录为专项外能力缺口，不在本专项实施。

### P1-1 页面骨架和内容容器不一致

- 用户管理使用裸表格，部门管理使用裸树，仓储/AI/知识使用各自卡片和页头；同一系统的边距、标题大小、筛选位置、空态和内容边界缺少共同节奏；
- `UserManagePage.vue`、`DepartmentManagePage.vue` 使用简单 `padding:1.5rem`，仓储、AI、知识分别重复定义页面头和容器；
- 后续只提取已经稳定重复的页面结构或共享样式，不预先建设通用页面生成器。

**目标规则**

- 收敛三类页面模板：列表页、树/主从页、诊断仪表页；
- 页面标题、辅助说明、主操作、筛选区、内容区、分页和空态有一致位置；
- 内容边界应帮助分组，但避免每一小块都套卡片造成层级过多。

### P1-2 AI 观测筛选过度挤压页头

- `/ai-observability` 把状态、业务结果、错误来源、Provider、工具、检索阶段、错误码和日期范围全部塞入页头右侧；
- 中等宽度下说明文字被挤成多行，筛选控件也变窄，首屏视觉重心混乱；
- 筛选应进入独立紧凑工具区，常用条件优先展示，低频条件可展开；已选条件要有摘要和一键清除。

### P1-3 表格、空态与操作层级仍缺少统一体验

- 用户列表数据较少时页面显得空旷，表格与分页缺少明确内容容器；
- 文本链接式“编辑/删除”在不同页面密度和危险层级不一致；
- 空数据页面大量显示“暂无数据”，没有解释筛选范围或可执行动作；
- 应统一行密度、表头对比、悬停态、空态动作和分页位置，同时保留既有长字段可读性、固定列和移动端规则。

### P1-4 仓储助手入口可能遮挡业务内容

- 多张截图中“打开仓储助手”悬浮在右下角，接近或覆盖表格操作区域；
- 需要验证在表格滚动到底部、分页和窄窗口下是否遮挡最后一行或操作按钮；
- 若存在遮挡，应预留安全区或将入口固定到不与业务动作竞争的位置，不回退已经确认的 OVERLAY/DRAWER 机制。

### P1-5 知识资料存在令牌与选中态一致性问题

- `KnowledgeDraftManagePage.vue` 选中草稿使用 `var(--ui-accent)`，但当前 `tokens.css` 没有定义该令牌；
- 草稿页与物品页同样使用原生文件控件，错误只显示裸文本；
- 该问题应纳入专项核对，但在 06F 浏览器链完成前不修改，避免混淆功能验收与视觉专项差异。

### P2 视觉细节

- 默认主题部分次级文字对比度偏低，需在不改变主题体系前提下验证可读性；
- 标题字号、卡片圆角、按钮高度和控件间距在各模块有小幅漂移；
- 图标与文本的对齐、危险色使用、加载骨架和键盘焦点需要统一走查；
- 不以像素级统一为目标，只修复用户能感知且影响识别/操作的问题。

## 5. 建议的实施边界与顺序

确认专项方向后先执行“批次 0”全系统扫描并提交问题台账供项目负责人复核；台账确认后，再按下列四个可独立验收的批次修改，不做一次性全站重写。
