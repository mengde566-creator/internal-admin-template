## 1. 为什么写这份方案

项目对测试的要求是：**测试必须从用户操作场景出发**。

当前的实际结果与此相反：测试全绿，用户第一次提问就失败（首问在进入 Provider 前失败）；随后又出现"发送按钮点了没反应""即时卡刷新后丢失"等完全没被测试覆盖的问题。已修复的真实缺陷由人工跑真实链发现，自动化测试没有发现其中任何一个。

本方案定义**测试资产怎么组织、怎么跟功能绑定、什么时候跑**，回答三个问题：

1. 一条测试的单位是什么；
2. 测试和话术资源算不算功能资产，怎么管理；
3. 开发一个新功能或修改一个功能时，测试怎么跟上去。

### 3.5 场景触发方式审计（回答"是不是又在测内部"）

68 个场景全部来自已确认的 `V0_2_WAREHOUSE_AGENT_SCENARIOS.md`，没有新增、也没有把内部概念改写成场景。按"谁触发、从哪个入口进"逐条审计：

| 触发方式 | 数量 | 说明 |
| --- | --- | --- |
| 用户在助手对话框或页面上直接做 | 50 | 提问、多轮澄清、乱码、注入话术、情绪、越界请求、双击发送、连点停止、断网、刷新、点赞、追问 |
| 需要构造 HTTP 请求（攻击者路径，页面做不了） | 2 | `SCN-AU-05` 伪造 departmentId/userId/权限数组、`SCN-AU-06` 枚举探测 |
| 管理员或运维在管理页面、部署时做 | 8 | 配置启用（`SCN-CFG-01`～`04`）、知识资料导入（`SCN-K-01/02`）、观测排查与评测运行（`SCN-OB-02/03`） |
| 用户会遇到，但无法主动触发，必须注入故障 | 7 | `SCN-E-02/03/04/07/08/09/10`（限流超时、Tool/知识不可用、History 写入失败、非法 JSON、错误码不一致、部分失败、内部字段泄漏） |
| 工程动作，不是运行时用户操作 | 1 | `SCN-RU-01` 移除适配后的构建证明 |

**结论**：场景本身是用户视角的，上一版的错误不在场景，而在**入口**——它是从内部 Service 和 Mock 模型边界进去测的。因此本方案追加一条硬规则：

> **每条场景测试必须写明用户入口**：页面操作、HTTP 请求、管理页操作，或"注入故障 + 用户观察结果"。**禁止从内部 Service、内部 Mapper 或测试专有装配进入**。没有用户入口的场景测试不予登记。

这也与场景文档 §13 的要求一致：首批样本中正常理想查询不超过 20%，其余覆盖真实修复、异常与攻击场景。

## 4. 体系设计

### 4.1 一条测试 = 一个用户操作场景

- 单位是**用户任务**，不是类、方法或接口；
- 断言只落在**用户可见结果**上：工具选择是否正确、卡片里的业务事实是否与仓储接口一致、终态是否唯一、刷新后 History 能否恢复、错误语义是否正确；
- **不断言**模型措辞、耗时、内部字段名——这既避免"加一个功能就推翻旧测试"，也让同一场景可以稳定复跑。

### 4.2 一个功能的完整资产

```text
需求文件（场景与验收标准）
  └─ 代码文件（后端接口 / 前端页面）
       └─ 后端场景测试（走真实 HTTP 正式接口）
       └─ 前端场景测试（走真实浏览器页面）
            └─ 共享话术资源（git 管理、带期望结果、带版本哈希）
```

四类缺一不可。**改动没有带对应场景测试与话术的，不算完成。**

### 4.3 三层执行

| 层 | 跑什么 | 触发时机 | 成本 |
| --- | --- | --- | --- |
| 快层 | 接口契约、状态机、权限边界、话术资源完整性（格式与哈希） | 每次改动 | 秒级 |
| 真跑层 | 整套话术集 + 真实 Provider + 真实数据库，走完整生产装配 | 一个功能块完成后整体跑一次 | 分钟级、消耗真实调用 |
| 页面层 | 真实浏览器主链：登录 → 打开助手 → 提问 → 看到卡片 → 刷新后从 History 恢复 | 功能块收尾 | 分钟级 |

三层共用**同一份话术资源**：真跑层与页面层跑同一组问法，只是入口不同。

页面层不可取消，理由是首问失败与发送按钮失效属于纯前端缺陷，HTTP 层测试无法发现。

**固定入口（写死后不再改命令）：**

| 层 | 固定命令 | 前置条件 |
| --- | --- | --- |
| 快层 | `./scripts/quality.sh --no-database` | 无（不需要应用在跑）；`--database` 另加隔离 SQLite 与空库启动 |
| 真跑层 | `./scripts/scenario-gate.sh` | 应用在跑（`./scripts/dev.sh start`）+ `SCENARIO_ADMIN_PASSWORD` |
| 页面层 | 待定（见 §8.0 未完成项） | 前后端都在跑 |

真跑层入口的稳定性来自三条约定，而不是来自命令里写死的类名：

1. 测试类按约定选择：`-Dtest='*ScenarioIT'`，**新增场景测试类不需要改命令**；
2. 凭据先取环境变量、缺失项再从仓库根 `.env.local` 读取（`SCENARIO_BASE_URL` 默认 `http://127.0.0.1:8080`，`SCENARIO_ADMIN_USER` 默认 `admin`，密码必填）；
3. 跑之前先做健康检查（`/actuator/health` 必须 200），跑之后**核验产物**：必须出现本次运行产生的 `*ScenarioIT` 报告、用例数大于 0、失败与错误为 0。选择器零匹配、被测类被环境条件跳过、只拿到上一次的旧报告，三种情况全部判失败。

### 4.3.1 为什么防线的重心在产物核验

`-Dtest=<选择器>` 在零匹配时不报错（配合 `-am` 必须保留 `-Dsurefire.failIfNoSpecifiedTests=false`），所以"选择了什么"不能作为通过依据；`target/surefire-reports` 又会跨运行保留，所以"报告存在"也不能作为通过依据。唯一可信的判据是**报告由本次运行产生**：门禁启动时写入时间标记，早于标记的报告一律判为陈旧、不计通过。该判据由 `scripts/assert-surefire-ran.sh` 单点实现，`quality.sh` 与 `scenario-gate.sh` 共用，避免两套实现各自漂移。

### 4.4 话术资源格式（已确认：沿用现有 schema，只做两处最小扩展）

现有单轮用例的 `steps[0].text` 扩展为 `texts[]`，语义是"这些问法都应得到同一期望结果"；新增 `scnRef` 指向已确认的场景编号。其余字段不变，不建立第二套资源格式。

```json
{
  "caseId": "stock-01",
  "scnRef": ["SCN-N-01"],
  "category": "BUSINESS_KNOWLEDGE",
  "split": "calibration",
  "executionMode": "END_TO_END_PROVIDER",
  "preconditionsRef": "warehouse-fixture",
  "steps": [
    {
      "texts": [
        "深沟球轴承还有多少",
        "查一下 ITEM-6204 的库存",
        "6204 轴承库存",
        "轴承类还有多少库存"
      ]
    }
  ],
  "requiresProviderRouting": true,
  "expectedBusinessOutcome": "ANSWERED",
  "expectedRunStatus": "COMPLETE",
  "expectedStableCode": "",
  "expectedToolSequence": ["warehouse_current_stock"],
  "forbiddenTools": [],
  "expectedCitation": {},
  "privacyAssertions": ["no_internal_id"],
  "maxProviderCalls": 4
}
```

资源要求：

- 位于业务模块的 `src/main/resources/evaluation/<业务>/`，与代码同仓库、同版本；
- 由 manifest 记录哈希，纳入快层校验；
- 话术不是临时字符串，不允许写在测试方法内部；
- 话术集分层：**核心子集**每次真跑，**全集**在功能块收尾与发版前跑。

**字段说明（2026-09-21 试点后补充，回答"期望看不懂"）**：

| 字段 | 大白话 | 谁在用 |
| --- | --- | --- |
| `caseId` | 用例编号 | 报告里标识这一条 |
| `scnRef` | 对应哪个已确认场景编号 | 场景对齐，人读 |
| `executionMode` | 怎么跑；`END_TO_END_PROVIDER` = 真调模型 | **仅人读**（执行器当前对所有用例同样执行） |
| `steps[].texts` | 同一个意图的一组问法 | 执行器逐条执行 |
| `expectedToolSequence` | 必须被调用的工具 | 执行器断言 |
| `forbiddenTools` | 本轮不得调用的工具 | 执行器断言 |
| `expectedRunStatus` | Run 必须到达的终态 | 执行器断言 |
| `expectedCard.cardType` | 必须出现的卡片类型 | 执行器断言 |
| `expectedCard.fieldsEqualBusinessFact` | 卡片里这些字段必须与业务接口事实逐字一致；期望值固定取自仓储查询接口，禁止测试自己编数字 | 执行器断言 |
| `knownIssues` | 已登记问题：每条含 `defectId`、`type`（`DEFECT` / `UNSTABLE`）、来源问法与已观测结果 | 执行器按"问法 → 类型"读取，始终显示但不阻断；台账见 [`KNOWN_DEFECTS.md`](KNOWN_DEFECTS.md) |

两条纪律：

1. **资源里只写执行器真正断言的东西**；确需保留的说明性字段必须在说明表里显式标成"**仅人读**"。独立复核实测：`scnRef`、`executionMode` 执行器引用为 **0 次**（`businessFactSource`、`placeholders` 属纯装饰，已删除）——它们只供人阅读，**不得被当成"已被检查的期望"**。
2. **一组话术只能有一种期望**。同一组里的问法必须是"同一意图的不同说法"（正式、简短、碎句、倒装、口语）；信息不完整的问法（例如只说"那个轴承"）会导致澄清，属于另一个场景（`SCN-RP-01`），不能混进同一组。

### 4.5 场景对齐（必须做的一次对照）

### 8.3 试点结论（2026-09-21，过程证据见台账）

**产物**：话术资源 `warehouse-stock-query-scenario-v1.json`（4 个用例、10 条问法）+ 执行器 `app-server/src/test/java/com/internaladmin/app/scenario/WarehouseStockQueryScenarioIT.java`。执行器只走真实 HTTP 打运行中的受管应用，需显式提供 `SCENARIO_BASE_URL`，不会被默认测试收集。

**试点期间被真实失败纠正的四处形态**（都是撞出来的，不是设想）：

1. **SSE 不携带工具事件**——真实事件只有 `run.started`、`message`、`card.replace`、`citation.added`、`message.completed`、`run.completed`、`run.failed`；`expectedToolSequence` 必须通过观测接口 `steps[].toolName` 断言；
2. **只写被断言的字段**——`scnRef`、`executionMode` 已标注"仅人读"；`businessFactSource`、`placeholders` 属纯装饰，已删除（执行器引用实测为 0 次）；
3. **LLM 场景本身不稳定**——同一问法跨轮次可失败可通过，因此取消"一次定论"：未登记的失败先复验 3 次，已登记项只跑 1 次；
4. **报告必须一次给全**——一条问法内跑完全部断言再汇总，并输出实际卡片类型、澄清候选、助手回复与 `runId`；这条直接省掉了多轮重跑。

**结论**：`DEF-001`、`DEF-002` 的修复经独立复核确认；`DEF-004` 同日发现并关闭；冻结基线整轮 **10 条全部通过**（其中 2 条被入口门禁拦截、未进模型）。**未完成项与已知缺陷一律登记在 [`KNOWN_DEFECTS.md`](KNOWN_DEFECTS.md)，本方案不复述过程。**

**副作用**：通过正式接口在研发库累计留下 **14 组** `SCNPILOT-*` 数据（独立复核实测：物品 14/35、仓库 14/31），未自行清理；它们会放大"未指定对象"时的库存概览，因此澄清类场景的断言只写"候选必须包含正确物品"，不写候选数量。
