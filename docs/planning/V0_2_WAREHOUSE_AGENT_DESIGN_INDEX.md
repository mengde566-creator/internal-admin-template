### 4.1 分片落地约束

- SLICE-00是仅用于证明技术纵链的例外节点，完成时没有用户可见入口；从SLICE-01起，每个产品分片都必须交付至少一条页面可见、可操作、可真实验收的用户链路。
- 开发前一次性冻结本分片的用户任务、功能、场景、页面、API、持久化和观测验收项；研发和验收必须证明同一用户操作链及最终可见结果，复核只处理契约冲突或主链阻塞，不追加理想能力。
- fake、mock和本地桩只用于确定性机制、异常分支和回归测试；纵向链达到可运行状态后，最终验收使用一次有预算的正式Provider调用，定位到明确实现缺陷后最多再复验一次。
- 正式Provider调用不是浪费；无目标的重复调用、压力测试和为了修复fake自身协议而反复消耗时间才是浪费。任何验证路径连续两次未增加主链证据时立即止损并改用最近的真实入口。
- 当前风险已被最低成本证据证明后即停止加码，不追求重复截图、重复抓包或多套等价证明。
- SLICE-01前必须补齐启用态POST Run接口的OpenAPI和前端类型契约；不得让前端根据后端实现猜请求或SSE结构。
- 每个分片收口必须明确列出“用户现在能看到和完成什么”以及“仍未包含什么”，避免把后端成功误报为产品功能已经落地。

### 4.2 SLICE-01交付边界

- 前端只在Agent已启用、`warehouse`适配可用且当前用户具有仓储查询权限时显示入口；关闭态不显示空壳按钮。
- 宽屏交付DOCKED和COMPACT，窄屏交付DRAWER；三种形态复用同一Conversation、History、输入草稿和运行状态，折叠或切换仓储页面不取消Run。
- 用户可以新建或选择本人Conversation、查看本人History、发送消息，并看到`run.started`、运行事件、受信卡片和唯一终态；网络或模型失败必须显示明确状态，不能显示成空回答。
- Task至少支持连续三轮补充、纠正和重新澄清；本分片验收Task与Memory是否正确，不要求提前完成SLICE-02的四个仓储Tool和完整业务卡片集。
- 允许把SLICE-00已有的单个库存Tool及`stock-summary`卡作为真实纵链回归和页面展示，不据此扩展其他Tool、复制、人工路由或知识引用能力。
- 本分片不实现异常输入全集、Knowledge问答、反馈、观测管理页和完整History管理页；它们仍分别归SLICE-03、SLICE-04和SLICE-05。

### 4.4 SLICE-04确认拆分与模拟数据时机

SLICE-03完成并通过总设计师复核后，SLICE-04已按`SLICE-04A → SLICE-04B → SLICE-04C → SLICE-04D`顺序实施。前三部分分别完成知识事实源、纯知识问答和知识与实时仓储混合查询；04D来自真实用户测试暴露的资料目录、完整资料读取与多文档选择场景缺口。该补充子任务对应独立用户结果，并非把后端引用、前端引用、提示注入或Provider验证机械拆开。

#### SLICE-04A：Knowledge资产生命周期与检索事实源

- 复用SLICE-00已有的固定目录、版本、切片、Embedding、pgvector和受权导入入口，不重建第二套知识系统；补齐Agent可以依赖的`KnowledgeQueryApi`公开契约。
- 将仓储操作制度、物品编码、仓库与库位编码、出入库/调拨/盘点规则和低库存处置规则整理为版本化合成资料；保留一个失效旧版本，覆盖幂等重导、内容变更、版本切换、零证据与运行期不可用。
- 模拟资料是本分片第一批研发输入，通过项目正式目录、正式导入服务、正式Embedding与生效版本链进入隔离知识库；禁止在SLICE-03结束后手工向数据库灌数据，也禁止用Liquibase业务种子或临时SQL伪造已索引状态。
- 研发阶段使用Stub验证确定性和异常分支；资料内容冻结后只进行一次有预算的正式Embedding导入与检索验收，确认内容哈希、维度、引用元数据和重复导入行为。不得反复修改语料来追逐测试结果。
- 本分片只交付知识事实源，不接入Agent回答，不建设上传、编辑器、OCR、通用ETL或知识管理页面。

#### SLICE-04B：纯知识问答与受信引用

- 用户可以用自然语言询问仓储制度、编码和操作规则；Agent只能依据`KnowledgeQueryApi`返回的当前生效片段回答。
- 后端生成受信引用并通过`citation.added`、`knowledge-answer`卡片和History传递，前端显示文档标题、版本及可核对片段来源；模型不得自行生成文档ID、版本或引用地址。
- 零证据时明确告知未找到依据，不用模型常识补答；知识片段中的提示、工具名或操作指令只作为正文，不得改变系统规则或触发Tool。
- 知识服务不可用时显示可见降级并保留已取得结果；本分片同时完成后端到前端的同一用户链，不另拆“前端引用分片”。

#### SLICE-04C：知识与实时仓储混合查询

- 覆盖“物品当前还有多少，以及低于制度阈值应该怎么办”一类同句任务；实时数量只来自Warehouse Tool，制度解释只来自Knowledge引用，两种事实不得互相代替。
- 多个互不依赖且参数完整的子任务按用户提及顺序执行并保留各自卡片；全部成功为完成，任一来源失败时保留成功事实并显示PARTIAL/DEGRADED。
- 用户重试时只重试失败子任务，不重放已成功的仓储Tool或知识检索；继续沿用SLICE-03已确认的Task、revision、scope、终态、取消和History约束。
- 实时仓储测试数据只进入项目隔离测试数据库并经正常业务入口产生，不写入知识文档；知识库也不得保存库存数量、库位余额或流水事实。

#### SLICE-04D：知识资料目录与完整资料读取

- 用户可以询问当前收录哪些资料、读取某份当前生效资料的完整受控内容，并在存在多个文档时通过受信选择继续；不要求用户提供内部文档ID或版本ID。
- 目录、当前版本、片段顺序、截断状态与引用均由服务端当前事实生成；首次完整问法可以定位唯一资料，多资料只澄清，旧版、过期或跨用户引用不得继续使用。
- 全文读取使用有界片段数和字符预算；Knowledge卡、History和前端使用同一严格合同，知识正文仍不得触发Warehouse Tool。

模拟数据虽不代表生产客户资料，但结构和生命周期必须按生产可用性设计：文档编码与版本稳定、来源可见、当前/失效状态明确、内容可分段引用、重复导入幂等、失败不产生部分生效索引。资料内容应足以支持真实自然问法、同义问法、零结果、旧版本和提示注入测试，不能只写为配合单条断言的一行Demo文本。

### 4.5 SLICE-05确认拆分

SLICE-05是“反馈、完整观测与评测”这一总体目标。根据03、04已经形成的真实运行链，实施前拆为三个可独立执行和验收的中型任务：

- `SLICE-05A`：完整运行观测与异常定位，补齐Task、Run、Step、Iteration、Attempt及模型、检索、Tool、流式、History终态的结构化事实和90天清理；不做反馈页面或评测。
- `SLICE-05B`：用户在线反馈与管理员诊断，完成本人完整回答赞踩、独立权限的概览、运行列表和时间线；不复制对话、知识或Tool正文。
- `SLICE-05C`：统一版本化离线评测，复用03、04已冻结语料和确定性断言，记录数据集、模型、配置、知识与规则版本；LLM评分不得覆盖权限、事实或引用失败。

03、04已经实现的History、SSE、取消、PARTIAL和失败子任务重试只进入05A验收矩阵；只有发现真实差值时才最小修正，不另立重复研发任务。

- 上传永不直接写物品或切换知识ACTIVE；物品采用影响预览后整批原子确认，知识采用草稿预览后显式发布。

### 4.7 2026-08-23 开发前差值审计

本次按“已确认需求 → 场景 → 功能 → 模块 → HTTP/SSE/数据 → 当前代码与测试”正向追踪，并以当前代码反向追溯消费者、权限和持久化事实；另由独立项目审议者直接读取原始材料做一次反例复核。审计当时结论是：**SLICE-01已有可见主链，但尚未收口，暂停直接进入SLICE-02生产实现。**以下五项契约纠偏已完成；最新交互状态以第 7 节为准。

进入SLICE-02前只完成一轮`SLICE-01契约纠偏`：

1. 落地最小持久化Task与`clarificationSelection`，以`taskId + revision + scopeFingerprint + expiresAt`校验旧候选；不建候选表、结果表或通用工作流。
2. 当时统一Tool结果为公共`outcome`和仓储窄DTO；该合同已由下述SLICE-03结构化结果复核取代。
3. 让Run请求、SSE信封、OpenAPI生成类型与前端消费者使用同一合同；补齐`occurredAt`、`memorySegmentId`，不再把`SseEmitter`当成业务响应Schema。
4. 收敛完整成功的原子边界：助手History、Run终态和Observation终态任一失败均不得向页面声明`SUCCESS`；不引入消息队列或分布式事务。
5. 归还Agent与Observability后续迁移的模块所有权；新增Task迁移只用四库共同类型与CAS，不使用部分唯一索引、JSON列、生成列或新的窗口函数。

本轮不夹带四类Tool全集、异常输入全集、Knowledge、反馈评测、保留期清理和第二业务消费者。现有窗口函数与历史迁移的低版本数据库门槛另立数据库兼容专项；它不阻塞当前已验证PostgreSQL上的功能落地，但完成前不得宣称MySQL/Oracle或任意低版本已验证兼容。

### 4.8 2026-08-27 SLICE-03结构化结果复核

- 通用API、Tool结果和模型最终结果只使用`success`、`code`、`message`、`data`四个顶层字段；成功码固定为`SUCCESS`，失败码使用可读稳定英文大写语义码；不使用`schemaVersion`、双编码或通用万能`data`容器。
- 结果码由最先掌握确定事实的后端或Tool产生；模型只能逐字传递本轮Tool失败码，后端校验来源，不重新查询数据库验证模型。
- 模型最终JSON在服务端完整缓冲并严格校验后一次性展示；SSE仍传输运行状态和已验证卡片，不展示未经验证的模型增量。
- 一轮多个Tool部分失败时保留成功卡片、Run为PARTIAL、最终`success=false`并从失败Tool代码中确定最终code；新Run只重试失败部分。
- 非法模型JSON最多自动修正一次，修正禁用Tool并只复用本Run缓存的安全结果；再次失败由后端返回`AI_MODEL_OUTPUT_INVALID`。
- 后端安全失败和已验证PARTIAL进入History但不进入Memory；非法模型输出、修正草稿、Tool原文和异常详情不进入History或Memory，继续任务只使用服务端受控Task中的已确认条件。
