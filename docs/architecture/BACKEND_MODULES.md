# 后端模块架构基线

> 状态：已确认  
> 版本：0.2
> 更新日期：2026-08-12

## 1. 架构结论

后端采用 Java、Spring Boot、Maven 多模块和模块化单体架构。当前所有模块由一个应用进程装配和运行，不拆分微服务，也不引入分布式基础设施。

如果后续出现真实的独立部署、独立扩缩容或团队边界需求，再针对需要拆分的业务模块评估 Spring Cloud。模块化单体是当前运行架构，清晰模块边界是未来可拆分的前提，但不是提前实现微服务兼容层的理由。

0.1 禁止引入 Spring Cloud、注册中心、配置中心、网关、OpenFeign、Bus、Stream 和分布式事务等微服务组件。

已确认的后端技术代际：

| 领域 | 基线 | 说明 |
| --- | --- | --- |
| Java | Java 25 LTS | 使用 25 的最新安全补丁，不追随非 LTS Java 版本 |
| 应用框架 | Spring Boot 4.1.x | 创建工程时锁定当时最新且验证通过的 4.1 补丁版本 |
| 数据访问 | MyBatis-Plus Boot 4 Starter | 以 3.5.17 为最低已验证候选，创建工程时锁定兼容的最新稳定补丁 |
| AI | Spring AI 2.0.x | 未来重点能力；出现首个已确认 AI 用例后再引入依赖和模块 |
| 微服务 | 暂不选择 Spring Cloud 版本 | 确认真实微服务拆分时再按 Spring Boot 兼容矩阵选择 |

选择 Spring Boot 4.1.x 的重要原因之一，是让未来接入 Spring AI 2.0.x 时不需要跨 Spring Boot 大版本迁移。这只确认技术兼容方向，不把任何尚未讨论的 AI 功能加入 0.1。

## 2. 目录与模块

```text
backend/
├─ pom.xml
├─ foundation/
│  ├─ platform-kernel/
│  ├─ platform-web/
│  ├─ platform-data/
│  └─ platform-security/
├─ modules/
│  ├─ module-iam/
│  ├─ module-file/
│  ├─ module-site/
│  ├─ module-audit/
│  └─ module-warehouse/
└─ apps/
   └─ app-server/
```

这份目录是已确认的工程骨架，不代表现在创建空目录或占位模块。只有进入工程实现阶段时，才一次创建能够参与 0.1 闭环并通过构建的真实模块。

## 3. 基础模块

基础模块提供与具体业务无关、且已经被多个业务模块共同需要的能力。基础模块禁止依赖业务模块。

| 模块 | 职责 | 禁止包含 |
| --- | --- | --- |
| `platform-kernel` | 最小公共类型、通用错误语义、模块事件基础约定 | HTTP、数据库访问、具体业务模型 |
| `platform-web` | Spring Web、参数校验、统一响应与异常边界 | 业务 Controller、业务权限规则 |
| `platform-data` | MyBatis-Plus、数据源选择、SQLite 默认模式、Liquibase 运行基础 | 业务表结构、业务 Mapper、业务 DO |
| `platform-security` | Spring Security 基础配置、当前登录身份和权限校验基础能力 | 用户业务表、角色管理流程、具体业务权限定义 |

基础模块只承载已经形成共同需求的能力。禁止为了“以后复用”向其中加入无调用方的工具类、扩展接口或通用业务框架。

## 4. 业务模块

业务模块按业务能力纵向组织自己的 Controller、Service、Mapper、DO、DTO、迁移和测试，不按技术层拆成全局 Controller 模块、Service 模块或 Mapper 模块。

| 模块 | 模板定位 | 0.1 职责 |
| --- | --- | --- |
| `module-iam` | 通用模板能力 | 根部门、最小内部用户与角色、管理员初始化、统一登录和权限能力 |
| `module-file` | 通用模板能力 | 本地文件存储、元数据、访问约束和模块对外文件能力；0.1 以展示图片验证 |
| `module-audit` | 通用模板能力 | 可被业务模块调用的最小操作审计；0.1 以 IAM 与站点动作验证 |
| `module-site` | 参考业务模块 | 公开主页草稿、预览、发布、撤回和匿名读取，用于证明完整模块装配链 |
| `module-warehouse` | 0.2 已确认业务模块 | 物品、仓库、库位、精确库存、人工库存操作和只读查询公开 API |

`module-site` 不是模板身份的核心。当前已经通过长期派生样本证明：移除该模块、对应前端注册、迁移聚合与契约装配后，IAM、工作台、数据库质量入口和开发启动仍然成立。该证据只证明 `site` 的一次真实裁剪，不自动证明任意模块都可自由移除；其他模块仍以各自契约和真实调用关系为准。

0.1 不因长期产品方向创建配置、字典、组织、工作流、通知、任务、AI 等空模块。对应需求确认并进入实现范围后，再增加真实模块。

## 5. 装配模块

`app-server` 是唯一应用装配和启动模块，负责：

- 引入当前应用需要的业务模块；
- 提供 Spring Boot 启动入口；
- 聚合应用级配置和各模块 Liquibase 主入口；
- 形成最终可运行应用。

`app-server` 不编写业务规则，不保存业务 DO，不直接访问业务 Mapper，也不作为跨模块调用的中转层。

## 6. 依赖方向

允许的总体方向是：

```text
app-server
    ↓
业务模块
    ↓
基础模块
```

必须遵守以下规则：

- `app-server` 可以依赖业务模块和必要的基础模块；
- 业务模块可以依赖必要的基础模块，禁止依赖 `app-server`；
- 基础模块之间只按明确职责建立单向依赖，禁止循环依赖；
- 基础模块禁止依赖任何业务模块；
- 业务模块禁止直接访问其他业务模块的 Mapper、DO、内部 Service 和内部表；
- 任意层级都禁止产生循环依赖。

具体 Maven 依赖必须按实际调用建立，禁止让每个业务模块机械依赖全部基础模块。

## 7. 模块公开边界

业务模块内部实现默认不向其他模块开放。跨业务模块协作只允许使用以下方式：

1. 同一进程内需要立即获得结果时，调用提供方明确公开的模块 API；
2. 已完成的业务动作只需要通知其他模块时，发布本地模块事件；
3. 禁止通过共享 Mapper、共享 DO、直接查询对方表或注入对方内部 Service 绕过边界。

模块公开 API 只暴露调用方需要的稳定契约和 DTO。不能因为采用多模块，就为每个内部 Service 机械增加接口；只有真实跨模块契约才建立对外接口。

当前已确认协作方式：

- `module-site` 通过 `module-file` 的公开 API 校验和使用展示图片，因为发布流程需要同步知道文件是否可用；
- `module-site` 与 `module-iam` 只共享中央注册的权限编码；文件管理使用独立 `file:manage`，不复用站点编辑权限；
- `module-site` 通过 `module-audit` 的公开 `AuditRecordApi` 同步记录发布和撤回结果，不访问审计内部表或 Mapper。

## 8. 数据库迁移归属

Liquibase 是结构变更的唯一入口，迁移文件按数据归属放在拥有该表的业务模块中：

- `module-iam` 维护身份与权限相关表的变更集；
- `module-file` 维护文件元数据相关表的变更集；
- `module-site` 维护主页草稿与发布相关表的变更集；
- `module-audit` 维护审计记录相关表的变更集；
- `app-server` 只按确定顺序聚合各模块变更集，不拥有业务表结构；
- `platform-data` 只提供 Liquibase 运行和多数据库基础能力，不集中保存全部业务迁移。

禁止一个业务模块直接修改另一个业务模块拥有的表。确需跨模块调整时，必须先确认模块契约和数据归属，再由表的拥有模块提供 Liquibase 变更。

## 9. 未来拆分为微服务的条件

只有模块出现明确的独立部署价值时才讨论微服务，例如：

- 需要独立扩缩容或故障隔离；
- 需要独立发布节奏和运行资源；
- 已形成稳定的数据与团队所有权边界；
- 单体内调用已经无法满足明确的非功能需求。

决定拆分后，再设计网络 API、服务发现、配置管理、容错、数据一致性和可观测性，并选择匹配版本的 Spring Cloud 组件。当前模块 API 和本地事件不承诺原样转换为远程调用。

## 10. 已落地基线与0.2已确认方向

已落地基线以父 POM、Maven Wrapper、锁文件和质量脚本为事实源：Java 25、Spring Boot 4.1.x、MyBatis-Plus 3.5.17、模块归属的 Liquibase 变更集及应用级聚合均已进入构建和测试。架构文档不再复制可能漂移的补丁版本与命令清单。

0.2已经确认以仓储作为第一个AI业务用例，继续采用模块化单体，不转微服务。目标模块边界为：

- `module-agent`：模型编排、会话、History、Memory和流式运行；
- `module-knowledge`：模拟知识、版本、Embedding和pgvector检索；
- `module-ai-observability`：run、step、反馈、评测和管理查询；
- `module-warehouse`：仓储领域、人工写页面与公开只读查询API；
- 仓储Agent适配模块：在Agent接入契约与仓储公开API之间做领域翻译。

这些是已确认的0.2目标模块；当前仅 `module-warehouse` 已进入实现目录，其余模块仍不得提前创建空目录或占位实现。完整依赖方向、数据所有权和PoC Gate以[`AI_CAPABILITY_SYSTEM.md`](AI_CAPABILITY_SYSTEM.md)为准。其余模块的裁剪与跨模块组合仍须在实际派生时验证，不能由单个参考业务的成功类推。
