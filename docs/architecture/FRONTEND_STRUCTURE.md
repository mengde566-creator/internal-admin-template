# 前端物理结构基线

> 状态：已确认  
> 版本：0.2
> 更新日期：2026-08-12

## 1. 架构结论

0.1 采用一个 Vue 3、TypeScript、Vite 前端工程，使用客户端渲染 SPA，形成一个构建产物。公开站点、登录页面、内部工作台和管理控制台是清晰的产品与权限边界，但不拆成多个前端工程。

单工程不代表混用页面、身份或权限。前端通过布局、路由分区、业务目录和动态导入保持边界，后端继续负责最终身份与权限校验。

0.1 不使用多个 Vue 应用、pnpm 多包工作区、Nuxt、SSR 或静态站点生成。

## 2. 产品界面与布局

```text
单个 Vue 应用
├─ 公开区域
│  └─ 公开站点布局
├─ 身份入口
│  └─ 登录布局
└─ 登录后区域
   ├─ 内部工作台
   └─ 管理控制台
```

- 公开站点使用独立公开布局，不展示内部菜单和登录后数据；
- 内部员工和管理员使用同一个内部登录入口、账号体系和登录状态；
- 0.1 使用服务端 Session 和安全 Cookie，长期演进方式见 [认证架构基线](AUTHENTICATION.md)；
- 登录成功后默认进入内部工作台；
- 管理员不是独立账号类型，而是拥有相应管理权限的内部账号；
- 工作台与管理控制台共用系统布局，通过路由、菜单和权限区分功能；
- 前端权限只改善导航和展示体验，不能替代后端 API 鉴权。

布局组件的最终文件名和具体视觉结构在前端骨架与原型阶段确认，不因本架构结论提前创建占位组件。

## 3. 代码组织方向

前端按产品与业务能力组织，不按所有页面、接口或组件的技术类型建立全局大目录。建议骨架是：

```text
frontend/
└─ src/
   ├─ app/                  # 启动、路由和全局配置
   ├─ layouts/              # 公开、登录和系统布局
   ├─ modules/
   │  ├─ auth/              # 登录、退出和当前用户
   │  ├─ workspace/         # 内部工作台
   │  ├─ site/              # 0.1 参考业务：主页管理、预览和公开展示
   │  ├─ file/              # 图片上传交互
   │  └─ iam/               # 0.1 最小账号与权限管理
   └─ shared/               # 已形成真实跨模块复用的基础能力
```

每个业务模块维护自己需要的页面、API、查询键、业务组件和路由注册。禁止提前创建没有页面或调用方的模块目录，也禁止把所有 API、类型和组件无边界堆积到 `shared`。

模板核心前端是 `app`、系统/登录布局、`shared` 基础设施以及 `auth`、`workspace`、`iam` 等通用内部管理能力。`site` 是随 0.1 提供的参考业务模块，不得把其公开路由、页面字段、布局枚举或内容模型变成其他派生项目必须接受的前端前提。后续需以真实裁剪验证证明移除 `site` 后模板仍能构建和进入内部工作台。

## 4. 加载与构建边界

- 页面路由使用动态导入；
- 匿名访问公开主页时，不应加载完整工作台和管理控制台代码；
- 内部用户没有对应权限时，不注册或不展示无权使用的管理导航；
- 是否有权限最终仍由后端决定，直接请求 API 不能绕过授权；
- 公开展示与管理预览可以复用同一业务展示组件，避免预览结果和真实公开页面产生两套实现；
- 开发阶段前后端独立运行，发布阶段可以把前端构建产物交由 Spring Boot 提供，也可以独立部署静态资源。

具体路由路径、构建输出目录和部署方式在工程骨架阶段确认。

## 5. 未来客户空间方向

未来可以在公开站点之外增加面向客户的登录与客户空间，用于提交反馈、合作意向或其他对外业务。该方向遵守以下边界：

- 外部客户是独立于内部员工的身份类别，不能简单作为内部权限体系中的一个角色；
- 客户空间与内部工作台使用不同登录入口和页面区域；
- 是否共享底层身份表、凭据服务或会话基础设施，需要在首个真实客户用例中设计；
- 同处一个 Vue 工程不代表客户与内部人员共享登录状态、菜单或 API 权限；
- 如果没有登录必要，反馈或合作意向可以先采用受控的匿名提交，不强制建设客户账号。

0.1 不创建外部账号表、客户权限、客户路由、客户页面或占位模块。未来方向不能反向扩大当前版本范围。

## 6. 将公开站点拆为独立应用的条件

只有出现明确收益时，才重新评估把公开站点或客户空间拆成独立前端应用，例如：

- 公开页面数量和内容规模明显增长；
- SEO、SSR 或静态生成成为已确认需求；
- 公开站点需要独立部署、发布或技术栈；
- 公开端与内部系统由不同团队长期独立维护；
- 单应用构建和发布已经产生可测量的问题。

拆分时根据真实页面和依赖提取代码，当前不建设多包共享层或跨应用兼容框架。
