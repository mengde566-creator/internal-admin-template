# Internal Admin Template 基础规划

> 状态：初稿  
> 日期：2026-07-18
> 定位：长期早期规划，不作为 0.1 实现依据

0.1 的实现范围只以 [已确认需求](../requirements/V0_1_SCOPE.md) 和已生效架构文档为准。本文件中超出 0.1 的模块、部署和兼容性设想不能自动进入实现。

## 1. 项目定位

`internal-admin-template` 是内部管理类应用的完整全栈基础模板，不是某个具体业务系统，也不是只生成后端目录的脚手架。

它应当解决两类问题：

1. 提供每个内部系统都会重复建设的通用模块；
2. 同时提供 Java 后端、Vue 前端、数据库设计和部署方案；
3. 给后续业务项目提供统一、可靠且容易裁剪的工程结构。

典型派生项目包括进销存、资产管理、客户管理、项目管理、工单系统和企业内部运营平台。

## 2. 目标与非目标

### 目标

- 克隆后可以快速启动一个完整的前后端开发环境；
- 未配置数据库时自动使用持久化的本地文件数据库；
- 通用模块具备真实生产可用的安全和审计能力；
- 业务模块之间有明确边界，便于独立演进；
- 可以按项目需要启用缓存、消息、对象存储和 AI 能力；
- 提供数据库模型、迁移、自动化测试、接口文档和部署样例；
- 派生项目能够明确记录自己相对模板的改动。

### 暂不追求

- 不在第一阶段拆成微服务；
- 不同时维护多套前端框架或多套数据访问框架；
- 不把所有可能用到的中间件设为必选项；
- 不预置复杂业务模块；
- 不为了“包含 AI”而提前引入 Python 服务。

## 3. 总体架构决策

### 3.1 模块化单体优先

第一版采用前后端分离的模块化单体：一个 Spring Boot 应用和一个主数据库；前端采用几个物理应用仍待确认。后端按业务能力划分 Maven 模块，并使用架构测试约束依赖方向。

这样既保留单体应用开发、部署和事务处理的简单性，也为将来确有需要时拆分模块留下边界。架构测试的具体工具在工程骨架阶段确认，业务代码不应依赖某个边界检查工具才能成立。

当前不引入 Spring Cloud。只有业务模块出现真实的独立部署、扩缩容或故障隔离需求并确认拆分为微服务后，才选择匹配版本的 Spring Cloud 组件。

### 3.2 Java 与 Python 的边界

Java 是默认且必须的后端技术栈。以下 AI 场景优先直接在 Java 中完成：

- 调用外部大模型 API；
- 结构化输出、流式对话和工具调用；
- 与业务权限、审计和事务紧密相关的 AI 功能；
- 常规知识库问答和 RAG。

Spring AI 已覆盖主流模型、向量库、工具调用、RAG、MCP 和可观测性，因此“使用 AI”本身并不构成引入 Python 的理由。

只有出现以下需求时，才增加独立 Python 服务：

- 模型训练、微调或 GPU 推理；
- 深度依赖 Python 专属的机器学习、OCR、图像或数据科学库；
- Notebook、实验流水线或复杂离线数据处理；
- 已有 Python 模型需要服务化。

Java 与 Python 初期通过 HTTP API 通信；需要长任务时再增加异步任务机制。两者不共享数据库表，权限判定和最终审计由 Java 主系统负责。

### 3.3 完整应用与交付方式

开发阶段保持 `backend` 与 `frontend` 分离，以获得良好的热更新和调试体验；发布阶段支持将 Vue 构建产物打入 Java 应用，生成一个可独立运行的发布包。

最终应提供三种运行方式：

1. 开发模式：一个脚本同时启动 Spring Boot 与 Vite；
2. 单机模式：运行发布包后同时提供 Web 页面、API 和本地 SQLite 数据库；
3. 部署模式：前后端可独立部署，并连接显式配置的外部数据库。

### 3.4 数据库选择与回退规则

数据库采用“零配置默认值 + 显式生产配置”的策略：

| 场景 | 数据库 | 行为 |
| --- | --- | --- |
| 未提供任何数据库配置 | SQLite 文件库 | 自动创建 `./data/internal-admin.db` 并执行迁移 |
| 本地自动化测试 | SQLite 临时库 | 快速验证通用逻辑 |
| 数据库兼容性测试 | Testcontainers | 分别验证 MySQL 与 PostgreSQL；Oracle 使用可用的测试环境或兼容容器 |
| 正常部署 | MySQL、Oracle 或 PostgreSQL | 通过环境变量显式提供类型、URL、用户名和密码 |

SQLite 是默认的本地持久化方案，不是生产数据库的行为模拟器。模板应避免依赖某个数据库的专属语法，并通过数据库方言、变更集分支和兼容性测试处理真实差异。

建议采用以下统一配置：

```text
APP_DATABASE_TYPE=sqlite|mysql|postgresql|oracle
APP_DATABASE_URL=<JDBC URL>
APP_DATABASE_USERNAME=<username>
APP_DATABASE_PASSWORD=<password>
```

完全没有数据库配置时才回退到 SQLite。只要用户提供了任意外部数据库配置但配置不完整或连接失败，应用必须启动失败并给出明确错误，不能静默回退到本地库，以免数据误写到错误位置。

微软 SQL Server LocalDB 不作为默认方案：它需要安装 SQL Server Express 组件、主要面向 Windows，并不能满足该模板的跨平台零安装目标。

## 4. 建议技术基线

以下是规划基线，创建工程时还要做一次依赖兼容性验证并锁定补丁版本。

### Java 后端

| 领域 | 建议 | 说明 |
| --- | --- | --- |
| JDK | Java 25 LTS | 使用 25 的最新安全补丁，不追随非 LTS 版本 |
| 框架 | Spring Boot 4.1.x | 创建工程时锁定验证通过的最新 4.1 补丁版本 |
| 构建 | Maven Wrapper | 降低环境差异，符合 Java 团队常见习惯 |
| 模块边界 | Maven 多模块 + 架构测试 | 边界检查工具待确认，不制造运行时耦合 |
| 微服务 | 0.1 不引入 Spring Cloud | 确认拆分微服务后再选择匹配组件和版本 |
| 安全 | Spring Security | 认证、授权和方法级权限 |
| 数据访问 | MyBatis-Plus Boot 4 Starter | 以 3.5.17 为最低候选，创建工程时锁定兼容的最新稳定补丁 |
| SQL 映射 | MyBatis Mapper + XML | 复杂查询显式编写并进行 SQL 审查 |
| 默认数据库 | SQLite | 零配置、持久化单文件数据库 |
| 外部数据库 | MySQL、Oracle、PostgreSQL | 正常部署时显式选择其中一种 |
| 数据迁移 | Liquibase | 结构化变更集优先，必要时按 DBMS 分支 |
| 缓存 | Redis，可选 | 无明确缓存或分布式需求时不启用 |
| API | REST + OpenAPI | 前后端契约和文档 |
| 测试 | JUnit + Testcontainers | 覆盖真实数据库集成测试 |
| AI | Spring AI 2.0.x，未来引入 | 出现已确认 AI 用例后再增加依赖，不进入 0.1 |

数据访问统一采用 MyBatis-Plus，不再引入 JPA/Hibernate。简单单表操作使用 `BaseMapper` 和类型安全的 Lambda Wrapper；联表查询、权限过滤、报表和性能敏感查询使用明确的 Mapper XML。

MyBatis-Plus Wrapper、分页对象和数据库实体不得直接暴露给 Controller 或前端协议，应用层使用独立的命令、查询对象和 DTO，避免数据访问框架渗透到业务接口。

运行时根据 `APP_DATABASE_TYPE` 配置 MyBatis-Plus 数据库类型和分页方言。通用 SQL 使用四种数据库都支持的语法；确实存在差异时，使用 MyBatis `databaseIdProvider` 为 SQLite、MySQL、PostgreSQL、Oracle 提供同一 Mapper 方法的数据库专用语句。

### Web 前端

Vue 3 可以作为本项目的正式前端方案。内部管理系统以表格、表单、筛选、权限路由和高频交互为主，Vue 3 + TypeScript 能够覆盖这些场景，并适合个人项目逐步迭代。

第一版采用客户端渲染的 SPA，不引入 Nuxt 或 SSR。内部管理系统没有搜索引擎收录需求，SSR 会增加认证、部署和数据加载复杂度，却没有对应收益。

| 领域 | 建议 | 说明 |
| --- | --- | --- |
| 运行时 | Node.js 24 LTS | 生产项目采用 LTS 线 |
| 框架 | Vue 3 | 适合中后台应用，生态成熟 |
| 语言 | TypeScript 严格模式 | 保证模板长期演进的可维护性 |
| 构建 | Vite | Vue 官方推荐的现代构建方案 |
| 包管理 | pnpm | 锁定依赖并提高安装效率 |
| 路由 | Vue Router | 路由懒加载、类型化 meta 和导航守卫 |
| 客户端状态 | Pinia | 只管理会话、权限、主题和跨页面界面状态 |
| 服务端状态 | TanStack Query for Vue | 请求去重、缓存、失效、重试和并发状态管理 |
| UI 组件库 | Element Plus，待原型确认 | 首选候选，验证表格、表单、主题和可访问性后锁定 |
| 单元/组件测试 | Vitest + Vue Test Utils | 与 Vite 共用转换链路 |
| 端到端测试 | Playwright | 覆盖 Chromium、Firefox 和 WebKit 关键链路 |

前端不是后端接口的演示页面，而是模板的一等组成部分，需要包含：

- 登录、工作台和完整管理布局；
- 菜单、路由和按钮级权限；
- 通用查询表格、表单、详情、批量操作和导入导出交互；
- 统一的请求、异常、加载、空状态和确认反馈；
- 主题、国际化预留、响应式适配和可访问性基础；
- 基于 OpenAPI 的类型或客户端生成，减少前后端契约漂移。

### 前端状态边界

- Pinia 不保存普通列表、详情和分页结果，避免把服务端状态做成难以失效的全局变量；
- TanStack Query 的 Query Key 按业务模块统一定义，禁止页面随意拼接；
- 字典、配置和组织树等低频变化数据可以设置较长的有效期；业务列表使用短有效期，并在新增、修改、删除后精确失效；
- 同一 Query Key 的并发请求应自动合并，页面卸载或筛选条件变化时取消已无意义的请求；
- 用户、权限和敏感信息不做无限期持久化缓存，退出登录时清空所有用户相关缓存；
- URL Query 保存分页、排序和筛选等可分享页面状态，避免刷新页面后条件全部丢失。

### 权限与路由

- 前端维护可静态分析的路由注册表，后端菜单通过稳定的页面编码关联路由，不下发任意组件文件路径；
- Vue Router `meta` 描述登录要求、页面权限和页面标题，导航守卫负责用户体验层的访问控制；
- 按钮和菜单隐藏只是界面体验，真正权限仍由 Java 后端校验；
- 页面组件使用动态导入实现按路由拆包，首屏不加载所有管理模块；
- 离开未保存表单时提供明确确认，防止误操作丢失数据。

### 表格与前端性能

- 列表默认使用后端分页、筛选和排序，不一次加载全部数据；
- 搜索输入防抖，远程下拉按关键字加载，并对旧请求进行取消；
- 普通表格优先使用稳定组件；只有单页确实需要展示大量行且服务端分页不适用时，才启用虚拟表格；
- 对大字典、树和选择器采用懒加载或虚拟化，不把整个组织数据重复复制到多个组件；
- 建立通用的 `DataTable`、`SearchForm`、`PermissionButton` 和 `EntityDialog` 等业务组件，但不无意义地二次封装每一个 UI 基础组件；
- 对构建产物设置体积预算，并在 CI 中执行 TypeScript 检查、单元测试和关键页面端到端测试。

### 可选 Python AI 服务

| 领域 | 建议 | 说明 |
| --- | --- | --- |
| Python | 3.13 起步，评估 3.14 | 优先验证目标 AI 依赖的兼容性 |
| 依赖管理 | `uv` + `pyproject.toml` | 使用锁文件保证环境可复现 |
| API | FastAPI | 仅在需要独立 Python 能力时引入 |
| 质量 | Ruff + Pyright/Pytest | 格式、静态检查和测试 |

Python 目录在第一个明确用例出现前不创建，避免模板用户承担无用依赖。

## 5. 规划中的目录结构

```text
internal-admin-template/
├─ backend/                 # Java 模块化单体
├─ frontend/                # Vue 管理端
├─ services/
│  └─ ai/                   # 可选；有明确用例后再创建
├─ deploy/                  # Docker Compose、部署配置和样例
├─ data/                    # 默认 SQLite 数据文件；不提交版本库
├─ docs/                    # 架构、决策、开发与派生指南
├─ scripts/                 # 跨环境的项目辅助脚本
├─ .editorconfig
├─ .gitignore
└─ README.md
```

后端按已确认的基础模块、业务模块和装配模块组织，而不是按 `controller/service/repository` 全局分层。完整说明见 [后端模块架构基线](architecture/BACKEND_MODULES.md)：

```text
backend/
├─ foundation/             # platform-kernel/web/data/security
├─ modules/                # module-iam/file/site/audit
└─ apps/                   # app-server
```

## 6. 模块范围

### 第一阶段：最小可用模板

- 用户与登录；
- 组织、部门和岗位；
- 角色、功能权限和基础数据权限；
- 菜单与路由资源；
- 参数配置与数据字典；
- 登录日志、操作审计和异常追踪；
- 统一错误、校验、分页、时间和 ID 约定；
- OpenAPI、数据库迁移、基础测试和本地部署。

### 第二阶段：常用增强模块

- 文件上传与对象存储适配；
- 通知中心与站内消息；
- 定时任务；
- Excel 导入导出；
- 可配置的数据脱敏；
- 单点登录/OIDC；
- 代码生成或页面生成能力。

### 第三阶段：按需能力

- 工作流；
- 多租户；
- 消息队列；
- AI 助手、知识库、智能填表或自然语言查询；
- Python 模型服务。

多租户和工作流不能作为第一版核心，因为它们会显著改变数据模型、权限模型和模块复杂度。

## 7. 数据库设计与兼容策略

数据库设计是模板的正式交付物。每个模块必须同时提供实体模型、表结构、索引、约束、变更集、初始化数据和数据字典说明。

### 7.1 初始数据域

| 数据域 | 初始表或关系 |
| --- | --- |
| 身份 | 用户、登录凭据、用户状态、会话/令牌 |
| 组织 | 组织单元、部门层级、岗位、用户组织关系 |
| 授权 | 角色、权限、用户角色、角色权限、数据范围 |
| 导航 | 菜单、路由、页面资源、按钮资源 |
| 配置 | 参数、字典类型、字典项 |
| 审计 | 登录日志、操作日志、安全事件、请求关联信息 |
| 文件 | 文件元数据、存储对象引用和访问控制 |

表名按业务域使用稳定前缀，例如 `iam_`、`org_`、`auth_`、`nav_`、`config_`、`audit_`，避免把所有表笼统命名为 `sys_*`。

### 7.2 可移植性约束

- 主键、布尔值、时间、文本长度、唯一约束和索引规则必须定义统一映射；
- 主键优先由应用生成 64 位 ID，避免依赖 MySQL 自增、Oracle 序列等数据库能力；API 中按字符串传输 ID，避免 JavaScript 大整数精度丢失；
- 时间统一按 UTC 存储，展示时转换到用户时区；
- 简单查询优先使用 MyBatis-Plus Lambda Wrapper，复杂 SQL 统一放在 Mapper XML 中；
- Mapper XML 默认使用可移植 SQL，数据库专属语句必须声明 `databaseId` 并提供必要的其他数据库实现；
- 排序字段必须使用服务端白名单，禁止把前端字符串直接拼入 SQL；谨慎使用 Wrapper 的 `apply`、`last` 等原生片段能力；
- 不把 Oracle 序列、PostgreSQL 数组、MySQL 枚举等专属能力放入通用核心；
- Liquibase 变更集优先使用结构化 change type，无法统一时用 `dbms` 条件提供差异实现；
- CI 必须在 SQLite、MySQL 和 PostgreSQL 上执行迁移与核心集成测试；Oracle 兼容性单独设立验证任务；
- SQLite 结构限制不能反向降低生产数据库设计，复杂迁移可采用建新表、搬迁数据、替换旧表的方式。

### 7.3 本地数据安全

- `data/` 默认加入 `.gitignore`，数据库文件不得提交；
- 首次启动创建管理员时必须要求修改初始凭据或完成初始化向导；
- 提供导出、备份、恢复和清空本地数据的明确命令；
- 不允许在数据库写入过程中直接复制文件作为备份；
- 切换外部数据库不会自动搬迁数据，数据迁移必须由显式命令完成。

## 8. 质量与安全底线

- 密码使用可靠的自适应哈希算法，密钥不得提交到仓库；
- 权限以后端判定为准，前端菜单隐藏不等于授权；
- 敏感操作记录操作者、时间、对象、结果和关联请求 ID；
- 数据库结构只通过 Liquibase 变更集变更；
- 单元测试、模块集成测试和关键链路端到端测试分层建设；
- CI 至少执行编译、静态检查、测试、迁移验证和依赖漏洞检查；
- 日志、指标、追踪使用统一的可观测性约定；
- 模板必须提供安全的默认配置，开发便利配置不得直接用于生产。

## 9. 实施路线图

### 里程碑 0：工程决策与骨架

- 确定许可证、包名、前端组件库、认证形态和 MyBatis-Plus 工程约定；
- 创建 Java、Vue 工程、SQLite 默认配置和外部数据库配置；
- 建立前端开发模式、后端开发模式和一键联合启动脚本；
- 用用户管理页完成前端原型，验证 Element Plus 的搜索、表格、分页、表单、弹窗、主题和权限按钮；
- 建立代码规范、CI、异常响应和 API 契约；
- 编写架构决策记录（ADR）与派生项目说明。

验收：新开发者不安装数据库、不填写数据库配置，仅依赖 README 即可启动完整系统；应用自动创建 SQLite 文件，Vue 首页能够调用后端健康检查；用户管理原型可以完成查询缓存、分页和编辑后的精确刷新。

### 里程碑 1：身份与权限闭环

- 完成用户登录、退出、会话续期；
- 完成组织、角色、菜单、功能权限；
- 实现后端权限测试和基础管理页面；
- 建立登录与操作审计。

验收：管理员能创建受限用户，该用户只能看到并调用被授权资源，越权请求被后端拒绝且可审计。

### 里程碑 2：模板产品化

- 补齐配置、字典、文件、通知等高频模块；
- 模块开关或裁剪指南；
- 初始化数据和演示数据分离；
- 发布、升级和从模板派生项目的操作说明。

验收：能够从模板派生一个示例业务模块，并在不修改核心模块的前提下完成 CRUD、权限和审计。

### 里程碑 3：AI 验证

- 选择一个真实、可衡量的内部管理场景；
- 先用 Java/Spring AI 完成最小实验；
- 只有实验明确需要 Python 生态时才创建 Python 服务；
- 记录成本、延迟、准确率、权限隔离和数据泄露风险。

验收：AI 功能关闭后不影响主系统；开启后所有数据访问仍服从业务权限并可审计。

## 10. 下一步需要确认的决策

按以下顺序推进，避免一次讨论过多选择：

1. 产品边界：单组织优先，还是从第一天支持多租户；
2. 后端基线：包名、构建插件和 MyBatis-Plus/SQLite 技术验证；
3. 前端组件库和整体视觉方向；
4. 第一阶段模块的数据模型；
5. 模板的派生和升级策略。

当前建议先按“完整全栈、单组织优先、模块化单体、Vue 3、SQLite 默认、外部数据库显式配置、Java 主栈、Python 按需”的方向进入里程碑 0。
