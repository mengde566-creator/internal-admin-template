# 0.1 交付成本复盘

> 日期：2026-08-12
> 复盘主责：总设计师 / 总架构师
> 核心结论：0.1 的工程结果可用，但交付成本失控；项目负责人报告约 200 美元 token 花费，与简单功能范围明显不成比例。

## 1. 责任结论

主要问题不是 0.1 功能复杂，而是总设计与调度把个人项目的小版本封版成了高合规、多角色、全证据链工程。每次暴露问题后继续增加任务、角色交接、报告和复验，导致治理成本反客为主。总设计师没有及时执行“最低必要复杂度”和投入产出止损，对此负主要责任。

本复盘不以“安全和质量很重要”解释成本。安全、测试和 CI 有真实价值，但不能合理化重复派单、重复全链运行、过度停等和文档膨胀。

### 1.1 二次复盘：更深层问题是模板目标被参考项目替换

在项目负责人重新明确“模板的重要性在项目前面”后复核，0.1 的严重问题不只是成本控制，而是成功标准发生了目标替换：

```text
原目标：证明这是一个可以启动、派生、裁剪和复用的模板
实际目标：证明公开主页参考应用安全、完整并通过发布验收
```

公开主页本来只是模板的第一条真实样例，执行中却成为版本中心。模板机制被写成业务闭环的配套物，资源优先用于主页发布、图片、草稿、E2E 和对应证据，而没有优先证明模板消费者最关心的操作。

| 模板应回答的问题 | 0.1 是否纳入完成标准 | 实际状态 |
| --- | --- | --- |
| 克隆后能否零配置启动 | 是 | 已证明 |
| 能否替换项目名、包名、应用标识和默认品牌 | 否 | 未证明 |
| 能否移除参考 `site` 模块后继续构建运行 | 否 | 未证明 |
| 能否只选择需要的通用模块 | 否 | 未证明 |
| 能否用同一能力包流程装入第二个小业务模块 | 否 | 未证明 |
| 派生项目是否有清楚、短小的操作说明 | 否 | 未证明 |
| 公开主页参考业务是否完整、安全、可发布 | 是，占据主要标准 | 已充分证明 |

因此，0.1 可以准确表述为“参考应用工程质量通过”，不能仅凭该结果宣称“模板成熟”。当前 README 和架构文档已经纠正这一区分。

### 1.2 根因链

1. **需求层目标不完整**：`V0_1_SCOPE.md` 的 12 条完成标准全部围绕启动和参考业务闭环，没有模板派生、改名、裁剪和二次装配验收。
2. **规划层沿用错误指标**：V01-05 至 V01-13 按契约、安全、测试、CI 和发布拆分，优化的是参考应用交付，没有设置“模板消费者旅程”。
3. **架构层没有标注模板层级**：基础模块、通用能力和 `module-site` 参考业务长期并列为“业务模块”，导致示例功能自然获得与模板核心相同的优先级。
4. **验证层倒置**：对参考业务执行了发布原子性、真实图片、浏览器和固定 SHA 验证，却没有执行一次“移除参考模块”的构建验证。
5. **治理层追求证据完整而非模板价值**：任务完成被等同于报告、测试和验收齐全；没有衡量这些产物是否让模板更容易被下一项目使用。
6. **成本层缺少止损**：即使任务和证据持续增加，也没有用模板价值增量重新审查预算。
7. **总设计师失守**：项目愿景早已说明这是可复用模板，但总设计师没有把愿景转换成版本完成标准，允许参考实现反过来定义版本。这是首要责任，不应归因于研发、运维、数据库限制或工具环境。

多对话交接、数据库权限限制、网络和测试环境只是放大器；即使这些问题全部消失，只要验收目标仍然错误，预算依然会优先花在参考项目而不是模板上。

### 1.3 本应在 0.1 开始前设置的模板门禁

如果当时坚持模板优先，0.1 在业务验收之外至少应有四项低成本门禁：

1. 从干净仓库按 README 启动；
2. 使用一份清单完成项目身份与默认品牌替换；
3. 移除 `site` 后端依赖、前端路由和迁移聚合后，IAM/工作台仍能构建运行；
4. 用能力包模板增加一个极小的第二业务模块，验证过程可重复。

这四项会在早期暴露真正的模板耦合，也会自然抑制继续扩张公开主页。它们比继续增加参考项目测试更直接地证明仓库价值。

## 3. 主要浪费来源

### 3.1 把所有问题都按最高风险任务处理

OpenAPI、Session、上传、IAM、Site、前端测试、CI、文档和发布被拆成 V01-05 至 V01-13，并继续拆为 A/B/预检/阻塞修复。高风险认证与发布原子性需要严格验证，但定位器、工作目录、等待时间和报告措辞不应获得相同治理强度。

### 3.2 可恢复错误被升级为跨角色阻塞

以下错误没有改变产品设计，却多次触发冻结、回报、重新派单和完整重跑：

- E2E 标签定位不精确、登录等待竞态、弹窗关闭名称不一致；
- 从仓库根目录而非 `frontend` 运行 npm；
- 临时运行器对响应码、权限字段和 64 位 ID 的假设错误；
- shell 变量、进程等待窗口和秘密宿主设计错误；
- 测试 JSON 格式化和 Spring 测试启动类歧义。

其中大部分应由当前执行者在同一任务内直接最小修正，而不是升级为新任务或等待总设计师再次授权。

### 3.3 “首个失败即停”使用过度

该规则适合数据库副作用、权限越界和未知破坏风险，不适合无副作用的命令目录、定位器或临时测试脚本错误。机械停在每个小错误上，使真实 E2E 串行暴露问题并形成多轮重新准备账号和环境。

### 3.4 真实主链探路太晚

前端 E2E 先完成大量测试定义，真实浏览器运行后才逐个暴露定位器、账号状态、导航竞态和组件可访问名称问题。更合理的顺序应是先跑一条最小真实主链探路，再补完整断言，最后只做一次源冻结发布验证。

### 3.5 角色边界变成了交接成本

研发、运维和总设计师的边界原本用于控制副作用，实际执行中却让编写、运行、修复和验收频繁跨对话往返。对于项目内隔离 SQLite 和无破坏性的局部验证，边界应控制目标与副作用，而不是禁止同一执行者完成闭环。

### 3.6 没有成本预算和停止条件

任务有网络等待和测试停止条件，却没有总任务数、最大失败轮次、文档数量或 token/费用止损线。结果是每次局部问题都继续追加流程，而没有在第三次返工时重新判断整体方案是否过重。

### 3.7 文档同步变成重复事实维护

任务书、实施报告、架构验收、能力包和总表多处重复当前状态。V01-12 完成后仍出现现行文档写“V01-12 待执行”，说明文档数量已经超过维护收益，并反过来制造新的收口工作。

## 4. 值得保留的实际产出

下列成果有真实价值，不应因成本失控而否定：

- Session 固定攻击防护、Cookie/CSRF 属性和退出清理；
- JPEG/PNG/WebP 真实内容校验、资源限制和失败清理；
- 初始化管理员与当前账号删除保护、角色引用和审计；
- 发布失败原子回滚、公开文件边界与草稿隔离；
- 草稿异步回填、空主图请求等真实前端缺陷修复；
- 本地/CI 同一质量入口、真实 Chromium 主链和可复现发布证据。

问题在于这些成果本可用更少任务、更少报告和更少全链重跑完成。

## 5. 更合理的 0.1 执行方式

如果重新执行，同等范围只拆三组：

1. **后端安全与高风险回归**：Session、上传、IAM、Site 一次完成；先最小编译，再一次隔离 SQLite 集成。
2. **前端与真实主链**：先跑一条最小浏览器探路，修正定位与账号前置，再补组件测试和完整 3 条 E2E。
3. **质量与发布**：建立一个质量脚本、一个 CI、一个最终矩阵；固定 SHA 后只做一次完整发布验证。

交付物控制为：最多 3 份紧凑任务记录、1 份最终验证报告和 1 份发布矩阵。失败历史压缩写入最终报告，不为每次失败生成独立长期文件。

## 6. 已实施的流程修正

本次复盘已同步修改唯一交付规则源 `VERSION_DELIVERY_PROTOCOL.md`：

- 增加 L0/L1/L2 分级，只有 L2 使用完整任务模板；
- 第三次失败、轮次超过预计两倍或治理文件多于产品与测试文件时强制成本止损；
- 工作目录、定位器、临时脚本和命令参数错误由当前执行者直接修复，不再新建任务；
- 同一固定源只保留一份最终证据；
- 真实 E2E 默认只保留早期探路和最终验证两轮；
- 无精确 token/费用数据时，用任务数、失败轮次、文件比例和耗时作为成本代理。

根 `AGENTS.md`、L2 任务模板和总设计师角色规范已同步引用该边界，避免规则只留在复盘文件。

## 7. 0.2 执行约束

0.2 开始前必须先做成本计划，不得直接沿用 0.1 的任务数量：

1. 每个里程碑先标 L0/L1/L2，并给出最多任务数和最多验证轮次；
2. 项目负责人给出 token/费用预算时，以预算为硬边界；无法读取精确花费时按代理指标在每个里程碑报告；
3. Agent 工程师仍只做已授权的知识库前置研究，不把预研扩大为正式运行时建设；
4. 同一功能第三次返工时，总设计师必须先向项目负责人报告投入、已产出和删减方案，不能继续自动追加流程；
5. 版本是否成功同时看功能结果、缺陷率和成本，文档数量与角色数量不再作为成熟度指标。

## 8. 最终评价

0.1 的工程质量达到了发布条件，但过程效率不合格。若只评价“是否最终通过”，会掩盖总设计失衡；正确结论是：产品结果通过，交付方法未通过。后续版本必须用已经落地的分级和止损规则证明成本下降，而不是再次用更多文档宣称已经吸取教训。
