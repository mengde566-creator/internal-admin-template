# 版本任务交付协议

> 状态：生效
> 版本：2.0
> 生效日期：2026-08-12
> 来源：V01-05 多轮返工复盘、V01-06 验收假绿风险、V01-09 真实 E2E 运行复盘、0.1 成本复盘，以及项目负责人关于跨版本防复发、关键链路禁止长时间等待和投入产出必须相称的明确要求
> 一句话规则：风险决定流程重量；L0/L1 由一个主责角色完成最小闭环，只有 L2 才启用完整派发、跨角色协作和独立验收。

## 1. 目的与适用范围

本协议把单次任务中的返工教训转化为 0.1、0.2 及后续版本必须重复执行的交付门禁，避免依赖某次对话记忆或某个人“记得”。

所有版本工作先读取第 2 节完成分级。L0 只执行轻量路径，L1 执行标准单人闭环，L2 才完整执行 Gate 0 至 Gate 4、版本工程任务模板和跨对话协作协议。禁止因为任务包含代码、编译或测试就自动升级为 L2。

## 2. 权威关系

- 根 `AGENTS.md` 规定何时必须加载本协议；本协议是跨版本交付流程的唯一稳定规则源。
- 具体需求、架构、接口和数据事实继续由各自权威文档定义，本协议不复制这些事实。
- 只有 L2 使用 [版本工程任务模板](templates/VERSION_ENGINEERING_TASK_TEMPLATE.md)；L0 不创建任务记录，L1 默认只在提交和最终回复中记录结果。
- 单次事故、实现报告和验收记录只保存本次证据；可复用的新教训必须回写本协议、模板、角色规范或自动化门禁，不能只留在任务记录中。

### 2.1 交付等级与成本止损

版本工作开始前必须先分级，禁止所有任务默认加载最高强度流程：

| 等级 | 适用范围 | 默认主责与记录 | 验证与验收 |
| --- | --- | --- | --- |
| L0 轻量 | 纯文档、明确配置、局部测试修正、单点缺陷；不改变数据、权限、公共 API 或运行架构 | 当前角色直接完成；不派发、不跨对话、不创建任务书或实施报告 | 执行一项最接近改动的检查；结果写入提交和最终回复，不要求独立验收 |
| L1 标准 | 单模块或单条用户链路；改动边界清楚且副作用可隔离 | 一个主责角色端到端完成；默认不创建任务书，确需跨会话或长时运行时最多一份紧凑记录 | 按风险执行局部测试和一次最终验证；总设计师做差异复核，不重复运行已可信的全链证据 |
| L2 高风险 | 数据模型、权限安全、公共契约、跨模块事务、迁移、外部部署或正式发布 | 总设计师派发，可按必要性分配多个角色；一份任务书和一份最终证据 | 完整执行 Gate 0 至 Gate 4；独立复现最高风险证据 |

典型路由：措辞、索引、测试定位器、命令目录和已知脚本小错属于 L0；单页面回填、单 Service 规则或单模块缺陷属于 L1；认证权限、数据库结构、公共契约和正式发布属于 L2。使用项目既有入口完成本地启动或状态检查属于 L0 运维动作，不因“启动服务”自动升级。

### 2.2 默认轻量路径

L0/L1 必须遵循以下默认路径，任何加重步骤都要说明它正在控制的具体风险：

1. 一个主责角色读取直接相关材料，确认范围和完成条件；
2. 先执行最便宜、最接近改动的静态检查或局部测试；
3. 在授权范围内完成实现、修正测试和必要验证，不因“研发/运维”标签拆开本可安全闭环的工作；
4. 检查差异后直接交付；L0 不等待总设计师二次验收，L1 只做一次差异与风险复核；
5. 只有出现 L2 风险触发器时才升级，不允许为了形式完整主动补任务书、接收回执、实施报告或验收报告。

L1 升级为 L2 的触发器只有：数据结构或迁移、权限与认证语义、公共 API/生成契约、跨模块事务一致性、不可逆或外部资源副作用、正式发布。文件数量多、包含测试、需要启动本地服务或需要两个技术步骤，本身都不是升级理由。

### 2.3 失败分类与恢复权限

失败发生后先分类，禁止把所有失败都称为阻塞：

| 类型 | 例子 | 处理方式 |
| --- | --- | --- |
| A. 可恢复执行错误 | 工作目录、命令参数、定位器拼写、临时脚本变量 | 当前执行者直接最小修正并继续一次，不新建任务、不切换角色、不重新申请授权 |
| B. 验证代码缺陷 | 测试样本、等待条件、Mock/fixture、测试配置错误 | 在原任务和文件范围内修正，先跑局部验证；不立即重跑完整 E2E |
| C. 范围内产品缺陷 | 当前功能的真实回归且修复不扩大契约 | 原主责角色补回归并闭环；只有需要扩大范围时才报告决策 |
| D. 风险阻塞 | 越权、未知数据副作用、不可逆动作、外部凭据缺失、架构/契约冲突 | 立即停止，保留现场并请求项目负责人或总设计师处理 |

“首个失败即停止”只适用于 D 类、可能污染状态的真实发布/E2E、或任务明确列出的高风险失败。A/B/C 类必须在原闭环内处理，不能机械冻结整个任务。

### 2.4 验证阶梯

验证按成本从低到高逐级推进，低层已经足以证明改动时不得追加高层：

1. 静态检查、格式和差异检查；
2. 定向单元或组件测试；
3. 单模块编译或集成测试；
4. 本地服务与单条主链探路；
5. 完整 E2E、数据库层、远端 CI 或发布验证。

L0 默认停在第 1 至 2 层，L1 默认停在第 2 至 3 层；只有相关风险无法在低层证明时才进入第 4 至 5 层。真实 E2E 仍默认最多两轮：一次早期主链探路、一次源冻结后的最终验证。

成本控制规则：

1. L0 只需在回复中声明等级和验证；L1 说明等级、最多验证轮次和止损点；L2 才在任务书中完整记录。项目负责人提供 token 或费用上限时必须遵守。
2. 同一任务达到第三次失败、实际轮次超过预计两倍，或新增治理/证据文件数量超过产品与测试变更文件数量时，总设计师必须暂停扩张，先重新判断任务设计是否过重。
3. 错误工作目录、定位器拼写、临时脚本变量、命令参数等可恢复执行错误，在没有越权副作用时由当前执行者直接最小修正并继续；禁止为每个错误新建任务、切换角色或等待总设计师再次授权。
4. 同一固定源只保留一份最终证据。失败历史在最终报告中压缩记录，不为每轮失败分别建立长期文档。
5. 真实 E2E 默认只运行“早期主链探路”和“源冻结后的最终验证”两轮；中间修复优先使用局部静态/组件验证。只有状态污染或高风险机制要求时才从头增加一轮，并说明原因。
6. 自动化、角色和文档的新增必须能减少后续重复成本；只增加审查步骤而不能机械阻断问题的规则应删除或降级为检查清单。
7. 无法取得精确 token/费用数据时，至少使用任务数、失败轮次、交付文件比例和实际耗时作为成本代理，不得以“质量重要”回避投入产出判断。

## 3. Gate 0：总设计师派发前可行性审查（仅 L2）

总设计师 / 总架构师在派发研发任务前必须亲自完成以下审查：

1. **事实基线**：列出当前权威需求、真实代码状态、历史记录和待确认事项，禁止把历史目标当成当前事实。
2. **能力矩阵**：逐项核对执行环境、权限、工具、依赖解析、网络、数据库边界、生成物来源和副作用。
3. **证据路径**：每一项完成标准必须对应当前允许环境中可实际执行的检查、命令或人工观察。
4. **最小探路验证**：对最高风险链路先做安全、最小的可行性验证，例如依赖解析、最小编译、接口语义或生成链路验证；数据库写入必须遵守根 `AGENTS.md` 第 8.0 节，未获项目负责人明确授权或未确认隔离目标时禁止执行。
5. **同步地图**：明确行为变化需要同步的代码、测试、契约、生成物和当前状态文档，以及历史记录的独立存放位置。
6. **反方审查**：主动寻找最可能导致任务无法完成、假通过或重复返工的条件，并给出处理方式。
7. **等待与升级预算**：为网络、依赖、编译、测试、启动和外部工具链写明进度信号、停止条件、最大重试次数、安全替代路径及需要项目负责人介入时的精确动作，并遵守根 `AGENTS.md` 第 2.2.1 节。

出现以下任一情况，任务不得派发：

- 完成依赖被禁止的操作或当前不存在的权限；
- 标准依赖解析、构建或关键工具链尚未证明可用；
- 要求提交生成物，却没有安全、可复现的生成路径；
- 完成标准只能写“应该可行”，没有可执行证据；
- 关键工具链没有等待停止条件、重试上限、安全替代路径评估或人工介入路径；
- 当前环境只能完成实现、不能完成最终集成验证，却没有把两者拆成不同状态和责任。

无法在当前环境完成最终验证时，必须把任务拆为“当前实现闭环”和“外部发布验证”，分别标明负责人、证据和状态，不能把不可执行条件直接交给研发兜底。

## 4. Gate 1：研发接单审查（仅 L2）

研发工程师在大范围修改前必须：

1. 读取本协议、任务书和任务关联的权威材料，不以历史对话记忆代替文件；
2. 复核任务范围、权限和每项完成标准的证据路径；
3. 尽早执行安全的依赖解析和最小编译或等价探路检查；
4. 发现完成标准不可执行、材料冲突或验证链路缺失时，立即携带证据退回总设计师，不得先实现再暴露问题；
5. 确认代码、测试、契约、生成物和文档分别由谁维护，避免平行事实源；
6. 对长操作确认进度信号和停止条件；达到停止条件或关键链路被阻塞时立即发送 `[任务 ID][阻塞]`，禁止重复同一失败路径，并说明需要的人工介入和仍可继续的独立工作。

接单审查不是重新设计产品。局部实现可以由研发判断；影响总体范围、公共契约、数据模型或验收标准的冲突必须退回总设计师收敛。

## 5. Gate 2：实现闭环（L1/L2）

实现必须形成一组最小但完整的连贯变更：

- 代码行为变化时，同步相关测试、契约与当前状态文档；
- 生成物必须由可复现流程产生，并被真实构建、测试或业务链路消费，不能只提交一个孤立文件；
- 新增工程骨架、依赖或配置后立即进行最小编译或等价检查，不能积累到最后统一发现；
- 正常路径与失败路径都必须可观察；关键漂移必须有拒绝或失败验证；
- 失败测试必须锁定目标规则的可观察结果；当同一输入可能被多条规则拒绝时，只断言“抛异常”或通用错误码不能证明指定规则生效；
- 承担验收语义的测试样本必须机械证明自身属性，例如固定来源与哈希、帧数、尺寸或损坏位置，不能只凭测试名称和说明文字认定；
- 文档开头描述当前真实状态，历史过程只放在明确标记的历史章节或证据文件中。

## 6. Gate 3：实现者自审（L1/L2）

实现完成后，主责角色必须脱离自己的实现叙述，重新从完成标准开始检查。L1 只执行与本次风险对应的条目，L2 执行完整清单：

1. 在安全且可复现的环境中重新执行适用的依赖解析、编译、测试和生成检查；
2. 同时验证正常路径和至少一个关键失败路径，例如契约漂移确实被拒绝；
   失败路径必须断言目标机制特有的结果，例如精确错误语义、状态变化、调用边界或样本属性，避免由其他拒绝路径造成假绿；
3. 对照权威来源检查实现、测试、生成物、接口契约和文档是否表达同一事实；
4. 搜索已过期措辞、旧状态和“当前事实写在历史记录里”的问题；
5. 确认生成物确实进入消费链路，权限和根 `AGENTS.md` 第 8.0 节数据库执行边界没有被绕过；
6. 发现问题后先修正，再重跑受影响的局部验证；只有公共源、构建链或有状态数据可能受影响时才重跑完整清单。

主责角色必须附带实际执行的证据、未执行项及原因。L1 自审和一次差异复核通过即可完成；L2 的自审通过只表示可以申请独立验收。

## 7. Gate 4：总设计师独立验收（仅 L2）

总设计师 / 总架构师不能直接采信研发结论，必须：

1. 逐项追溯任务目标、变更和证据，确认没有靠修改验收口径取得通过；
2. 独立复现最高风险检查和关键失败路径；
   对多重失败条件的样本必须确认实际触发的是待验收规则，不能仅以最终失败作为通过依据；
3. 检查权限、副作用和根 `AGENTS.md` 第 8.0 节数据库执行边界；
4. 检查当前文档、历史记录和实现状态是否一致；
5. 对未执行验证明确影响，不把部分闭环标记为完整完成；
6. 只有全部阻塞项关闭后，才由总设计师更新任务状态并通知项目负责人。

## 8. 反馈闭环

同类问题第二次出现，或一次问题暴露出系统性缺口时，总设计师先判断是“已有规则未执行”还是“确实缺少机制”。已有规则足以覆盖时只纠正执行，不再新增文档；只有新机制能够机械阻断复发并降低后续成本时，才选择一种长期修正：

- 稳定判断规则更新到本协议；
- 固定信息字段更新到任务模板；
- 角色责任缺口更新到对应角色文档；
- 可以机械判定的规则落为脚本或 CI，并由文档指向该实现；
- 仍需人的语义判断则保留为人工门禁，不夸大自动化能力。

规则只能有一个权威来源。其他文档应引用本协议，不得复制后形成多个版本。

## 9. 历史高风险规则（按任务风险加载）

以下规则来自 V01-05 的多轮返工与 V01-06 的验收假绿风险。只加载与当前任务风险直接相关的条目，L0/L1 不为无关历史问题增加检查：

1. 生成物不得依赖会触发被禁止副作用的应用启动路径；数据库不可用时，契约生成仍须有安全路径，或任务必须明确标为外部验证。
2. 引入或调整依赖前必须先证明标准依赖解析可行，不能把工具链问题留到完整实现之后。
3. 新工程骨架必须尽早最小编译，禁止一次堆叠大量代码后才发现基础结构不成立。
4. 生成物必须进入真实消费链路；“文件存在”不等于能力已经落地。
5. 当前状态与历史记录必须分开；验收优先检查当前真相，不用历史措辞掩盖现状。
6. L2 的研发自我复盘是提交总设计师验收的前置证据，不是最终验收结论；L0/L1 按第 2 节直接闭环。
7. 总设计师对任务本身是否可执行负责；不可执行的任务不能通过要求研发多改几轮来补救。
8. 安全阈值、权限边界、契约漂移等规则必须由机制特异性断言证明；通用异常、通用状态码或“结果失败”不足以证明目标规则存在。
9. 截断、损坏等同时包含多种失败条件的样本，不能单独证明尺寸、像素、帧数等另一条规则；必须断言精确原因、直接机械核验样本属性，或使用只违反目标规则的有效样本。
10. 外部固定样本必须记录来源、不可变版本和校验值；当样本语义属于验收条件时，自动化测试还必须校验相应哈希或结构属性，防止样本漂移后测试继续假绿。
11. 网络、依赖、编译、测试、启动和外部工具等待必须有界；达到停止条件后按第 2.3 节分类。只有风险阻塞或同一实质路径再次失败才请求人工介入，普通执行错误由当前角色直接修正。
12. `playwright test --list`、静态规格审查和 Mock 网络测试只能证明 E2E 用例存在，不能证明真实浏览器链路可运行。真实 E2E 前必须明确账号状态、权限、一次性数据、导航稳定条件和隔离目录；可能污染状态或产品失败时停止并保留证据，定位器、等待和临时运行器错误按 B 类在原任务内修正，先做局部验证，最终只补一次完整链路。

## 11. 跨对话协作与回报（仅 L2 或真实多角色并行）

只有任务已经判定为 L2，或多角色并行确实降低总成本时才执行以下规则。L0 禁止跨对话派发，L1 默认单角色闭环：

1. L2 在任务书中写明执行对话、上游总设计师对话、可修改文件和禁止文件；特殊 L1 并行只在当前对话写一条紧凑所有权记录。
2. 执行对话收到任务后，必须先通过 Codex 的跨对话消息能力向总设计师对话发送“已接收”回执，再开始大范围修改。消息目标由 L2 任务书或特殊 L1 的紧凑所有权记录提供。
3. 执行中出现范围冲突、不可执行标准、需要修改公共文件或 D 类风险阻塞时，必须立即向总设计师对话发送阻塞消息；A/B/C 类按第 2.3 节由原主责角色处理。
4. L2 完成自我复盘后向总设计师发送验收申请，包含任务 ID、结论、最终证据、实际验证、未执行项、风险和文件范围；特殊 L1 并行只发送一次简短完成回报。
5. 如果当前对话没有跨对话消息工具，必须如实说明；L2 将最终证据写入任务文件，L1 直接在当前对话报告，禁止假称消息已发送。
6. 总设计师是跨对话调度中心。研发对话不得直接改变另一研发任务的范围、状态和文件所有权。
7. 共享工作区的构建产物同样属于共享资源。并行期间禁止执行会删除公共构建产物的 `clean`；需要全量清理或跨任务集成验证时，由总设计师在两个任务源文件冻结后统一执行。

跨对话消息建议使用以下固定格式：

```text
[任务ID][接收/阻塞/申请验收]
当前结论：...
证据文件：...
已执行验证：...
未执行项/风险：...
需要总设计师处理：...
```
