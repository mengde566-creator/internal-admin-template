# 版本任务交付协议

> 状态：试运行
> 版本：2.3
> 生效日期：2026-08-12
> 来源：V01-05 多轮返工复盘、V01-06 验收假绿风险、V01-09 真实 E2E 运行复盘、0.1 成本复盘、独立项目审议，以及项目负责人关于禁止简单事情复杂化、关键链路禁止长时间等待和投入产出必须相称的明确要求
> 一句话规则：风险只决定证据强度，不自动增加角色、文档和审批；所有等级默认由一个主责角色完成最小闭环。
> 试运行边界：只选择下一项真实、低风险的模板派生任务验证本方法，不扩展公开主页；只记录五类实测成本，不预设比例审批阈值。试验结论提交项目负责人后再决定是否正式生效。

## 1. 目的与适用范围

本协议把单次任务中的返工教训转化为 0.1、0.2 及后续版本必须重复执行的交付门禁，避免依赖某次对话记忆或某个人“记得”。

所有版本工作先读取第 2 节完成分级。L0、L1、L2 均默认执行单人最小闭环；L2 只加强与最高风险直接对应的证据，并按适用范围执行 Gate 0 至 Gate 4。禁止因为任务包含代码、编译、测试或高风险标签就自动增加任务书、角色、跨对话交接和重复验收。

## 2. 权威关系

- 根 `AGENTS.md` 规定何时必须加载本协议；本协议是跨版本交付流程的唯一稳定规则源。
- 具体需求、架构、接口和数据事实继续由各自权威文档定义，本协议不复制这些事实。
- L0/L1 默认只在提交和最终回复中记录结果。L2 也默认使用当前任务中的紧凑基线；只有真实多角色文件所有权交接、外部验证交接或不可逆操作需要书面授权时，才使用 [版本工程任务模板](templates/VERSION_ENGINEERING_TASK_TEMPLATE.md)，且整个任务只保留一份任务记录和一份最终证据。
- 单次事故、实现报告和验收记录只保存本次证据；可复用的新教训必须回写本协议、模板、角色规范或自动化门禁，不能只留在任务记录中。

### 2.1 交付等级与成本止损

版本工作开始前必须先分级，禁止所有任务默认加载最高强度流程：

| 等级 | 适用范围 | 默认主责与记录 | 验证与验收 |
| --- | --- | --- | --- |
| L0 轻量 | 不改变生产行为、运行配置、依赖、质量门禁、验收语义或治理权责的机械调整 | 一个职责适格的主责角色直接完成；需要跨角色时只路由一次，不创建任务书或实施报告 | 执行一项最接近改动的检查；结果写入提交和最终回复，不要求独立验收 |
| L1 标准 | 改变单模块、单页面或本地运行脚本行为，但不触发任何 L2 风险 | 一个主责角色端到端完成；默认不创建任务书，确需跨会话或长时运行时最多一份紧凑记录 | 回归测试或真实受影响入口至少一项，加一次差异复核；不重复运行无关全链证据 |
| L2 高风险 | 触发下列任一高风险条件 | 一个主责角色端到端完成；仅存在真实文件所有权或证据权限缺口时增加一名必要协作者 | 按适用范围执行 Gate 0 至 Gate 3；只有第 7 节条件成立时才独立复现最高风险证据，不重复整个验证链 |

分级必须按以下顺序判断，风险优先于文件数和代码行数：

1. 命中 L2 触发器，直接定为 L2；
2. 未命中 L2，但改变生产行为、运行配置或项目脚本行为，定为 L1；
3. 只有不改变运行与验收语义的机械调整才是 L0；
4. 无法确定影响时暂按高一级处理，完成定向只读核对后可以降级并说明依据。

L2 触发器：

- 认证、授权、安全边界，以及敏感信息/用户隐私的收集、存储、传输、暴露或清理行为；
- 数据结构、Liquibase、数据修复、非一次性数据写入或跨模块事务一致性；
- 已确认需求范围、总体架构、模板边界、公共 API、生成契约、模块边界或跨模块依赖方向；
- 运行时依赖的新增、删除或版本变更，以及构建工具链、质量门禁、CI/CD、发布与外部部署；
- 不可逆操作，外部资源的创建、修改或删除，真实凭据、共享/生产环境；
- 根 `AGENTS.md`、本协议、角色决策权限、强制验收规则等底层治理变更。

典型路由回放：

| 场景 | 等级 | 理由 |
| --- | --- | --- |
| 文档错字、索引链接 | L0 | 不改变行为 |
| E2E 定位器精确化 | L0 | 仅当断言和验收语义不变；否则重新分级 |
| 错误工作目录后改用已有正确命令 | L0 | 未产生副作用且不改仓库行为 |
| 页面异步回填缺陷 | L1 | 单页面生产行为与回归测试闭环 |
| `dev.sh` 优雅停止等待窗口 | L1 | 本地脚本行为，需真实生命周期验证但不涉及发布策略 |
| Session/Cookie、上传安全、权限删除保护 | L2 | 认证、授权或安全边界 |
| `quality.sh`、GitHub Actions、依赖版本 | L2 | 影响所有后续交付可信度 |
| 修改本协议或角色决策权限 | L2 | 改变全部后续任务的执行规则 |

### 2.2 默认生产路径

所有等级必须遵循以下默认路径，任何加重步骤都要说明它正在控制的具体风险，以及为什么更轻证据不足：

1. 一个职责适格的主责角色读取直接相关材料，确认范围和完成条件；
2. 先执行最便宜、最接近改动的静态检查或局部测试；
3. 在授权范围内完成实现、修正测试和必要验证，不因“研发/运维”标签拆开本可安全闭环的工作；
4. 检查差异后直接交付；L0 不等待二次验收，L1 只做一次差异与风险复核；L2 先以机制特异性自动化和主责自审闭环，只有第 7 节条件成立时才增加最高风险独立复核；
5. 只有出现真实文件所有权、证据权限或不可逆授权缺口时才增加交接或记录，不允许为了形式完整主动补任务书、接收回执、实施报告或逐轮验收报告。

角色名称、文件数量、是否包含测试、是否需要启动本地服务或技术步骤数量都不能单独决定等级；它们既不能把 L1 自动升为 L2，也不能把命中高风险触发器的任务降级。

根 `AGENTS.md` 第 1.5 节“禁止简单事情复杂化”是本协议的硬性红线。高风险只允许加强具体风险证据，不能作为扩大团队、报告、审批、等待或全量验证的通行证。项目负责人指出流程过重时，当前执行者必须立即停止继续加码，回到目标、最小范围、最近证据和剩余风险四项重新收敛。

#### 2.2.1 角色路由硬边界

角色路由按工作性质决定，不按当前对话是谁、谁先看见任务或用户使用了哪个动作词决定：

1. 总设计师 / 总架构师主责产品意图收敛、需求与架构边界、任务分级、实现范围、角色路由和架构差异复核；可以亲自维护团队治理、角色边界和架构决策类文档。
2. 研发工程师是应用生产实现的默认执行者，负责生产代码、应用运行配置、应用依赖、生成物、已确认接口契约的实现与同步、实现测试及其直接联动技术文档。用户明确指定其他职责适格角色，或已有角色文档明确资产归属时，按该角色执行。
3. 运维工程师负责部署配置、CI/CD 工作流、运行环境、启动与部署脚本、质量入口和运行手册；业务构建缺陷由研发修复，质量入口与 CI 编排由运维维护。资产同时涉及应用行为和运行编排时，总设计师只划定一次文件与决策边界，不亲自实施。
4. 项目负责人对总设计师说“进行”“创建”“修改”“开始”“继续”等结果型指令，只表示授权团队推进该结果；总设计师必须先路由，不得解释为自己获得了执行职责。只有项目负责人明确说“由总设计师亲自实现/修改”时才构成例外。
5. 研发或运维接单后在各自资产范围内完成最小连贯实现、自审和与风险最近的验证。该规则不建立研发→测试→运维→总设计师的固定流水线；只有第 7 节或真实环境权限缺口触发时才增加一次必要协作。
6. 总设计师可以只读检查代码、复核差异、提出阻塞问题并验收架构符合度，但不得借“先探路”“顺手修复”“避免交接”直接写入第 2、3 项文件。发现自己已越界时立即停止继续实现，保留已产生差异并交给职责适格角色复核；不得为了纠正角色错误而机械撤销正确产物或重做同义实现。

本边界控制的是职责错位，不是增加审批。一次任务只发生一次“必要边界收敛→职责适格角色执行”交接；简单应用任务由研发单角色闭环，简单运维任务由运维单角色闭环，不要求接收回执、任务书、实施报告或总设计师逐项验收。

### 2.3 失败分类与恢复权限

失败发生后先分类，禁止把所有失败都称为阻塞：

| 类型 | 例子 | 处理方式 |
| --- | --- | --- |
| A. 可恢复执行错误 | 错误工作目录、已有命令参数误用、临时运行器拼写 | 仅在未产生副作用、未污染状态、且修正不改变源码/验收语义时，由当前执行者直接纠正一次 |
| B. 验证代码缺陷 | 定位器、等待条件、fixture、测试配置错误 | 仅在原授权文件范围内修正，不得删除/减弱断言；改变验收语义时重新分级并请求确认 |
| C. 范围内产品缺陷 | 当前功能的真实回归且修复不扩大契约 | 至少按 L1，由拥有业务文件权限的主责角色补回归并闭环；角色职责和文件所有权不得因分类自动扩大 |
| D. 风险阻塞 | 越权、未知数据副作用、不可逆动作、外部凭据缺失、架构/契约冲突 | 立即停止，保留现场并请求项目负责人或总设计师处理 |

“首个失败即停止”只适用于 D 类、已经产生或可能继续扩大状态污染的真实发布/E2E、或任务明确列出的高风险失败。A/B/C 类按表中权限处理，但任何修正一旦扩大文件、产品语义、验收标准或副作用，必须先重新分级。

### 2.4 验证阶梯

验证按成本从低到高逐级推进，低层已经足以证明改动时不得追加高层：

1. 静态检查、格式和差异检查；
2. 定向单元或组件测试；
3. 单模块编译或集成测试；
4. 本地服务与单条主链探路；
5. 完整 E2E、数据库层、远端 CI 或发布验证。

L0 默认停在第 1 至 2 层，L1 默认停在第 2 至 3 层；只有相关风险无法在低层证明时才进入第 4 至 5 层。早期主链探路只证明环境和主路径可达，不算完整验收。源冻结后只执行一次最终完整验证；探路已经覆盖且源未变化的步骤不得在最终验证前反复重跑。

最低证据不得低于下表；更高层验证只有在风险无法被最低证据覆盖时增加：

| 变更 | 最低证据 |
| --- | --- |
| 文档、索引、格式 | 链接/定向检索或语法检查 + 差异检查 |
| 测试定位器、fixture、等待 | 测试发现或目标测试 + 确认断言语义未减弱 |
| 单模块生产缺陷 | 能复现问题的回归测试 + 相关模块编译/测试 |
| 本地运行脚本 | 语法/静态检查 + 在允许环境执行受影响生命周期一次 |
| L2 | 紧凑基线为最高风险指定机制特异性证据；不得用低层检查替代安全、数据、契约或发布验证，也不得为低风险 AC 重复增加同层证据 |

“一个主责角色端到端完成”只减少交接，不扩大其既有权限、数据库权限、外部系统权限或文件所有权。

成本控制规则：

1. L0 只需在回复中声明等级和验证；L1/L2 说明等级、证据预算、最多验证轮次和止损点。只有真实交接或不可逆授权才创建任务文件。项目负责人提供 token 或费用上限时必须遵守。
2. 同一任务达到第三次失败、实际轮次超过预计两倍，或新增治理/证据文件数量超过产品与测试变更文件数量时，总设计师必须暂停扩张，先重新判断任务设计是否过重。
3. 错误工作目录、定位器拼写、临时脚本变量、命令参数等可恢复执行错误，在没有越权副作用时由当前执行者直接最小修正并继续；禁止为每个错误新建任务、切换角色或等待总设计师再次授权。
4. 同一固定源只保留一份最终证据。失败历史在最终报告中压缩记录，不为每轮失败分别建立长期文档。
5. 真实 E2E 最多允许一次早期主链探路和一次源冻结后的最终完整验证；早期探路不计为完整通过。中间修复优先使用局部静态/组件验证。只有状态污染或源变化无法由局部证据排除时才增加完整轮次，并事先说明原因与成本。
6. 自动化、角色和文档的新增必须能减少后续重复成本；只增加审查步骤而不能机械阻断问题的规则应删除或降级为检查清单。
7. 开展流程试验或已有成本数据时，分别记录实现、测试编写与修复、测试执行与环境等待、人工验收、协调与报告五类实测成本；没有可信基线时不设置预测比例和审批阈值。任何任务都不得以“质量重要”回避已经明显失衡的投入产出。

### 2.5 用户视角验收

自动化验证负责证明可机械回归的行为，项目负责人保留业务、体验与发布的最终判断权。验收按风险聚焦，不平均用力：影响面、不可逆性、权限/安全/金额/时间等敏感边界会提高风险；仅局部展示、可快速回退且无数据副作用的变化保持轻量。

- L0 只核对受影响结果，不创建测试文档或验收清单；
- 用户可见或存在用户操作路径的 L1，由主责角色依据已确认需求完成回归，并用一次用户视角走查检查入口是否可发现、主流程是否顺畅、错误是否可理解；纯配置或后端内部任务只执行与风险最近的验证；
- L2 只对最高风险增加机制特异性证据；自动化无法表达的视觉、文案和操作体验由项目负责人抽查，不因此复制一套技术验收；
- 只有一个模块存在长期人工回归需要时，才建立一份“操作 + 预期”清单；可自动化的内容应落为代码测试，禁止同时维护同义的测试文档、实施报告和验收报告。

验收发现的问题回到当前需求、回归测试或唯一稳定规则源。一次性体验判断留在提交与最终回复，不为普通任务建立长期验收档案。

## 3. Gate 0：最高风险可行性审查（仅 L2）

L2 实现开始前，主责角色必须完成以下紧凑审查；涉及需求、总体架构、模板边界或治理权责的决定由总设计师 / 总架构师确认，其他高风险任务不得仅为完成本 Gate 强制转交总设计师：

以下条目只回答与当前任务实际相关的部分；没有长操作、外部依赖、生成物或文档同步时，直接略过对应条目，禁止为填写本 Gate 另建表格、报告或审批记录。

1. **事实基线**：列出当前权威需求、真实代码状态、历史记录和待确认事项，禁止把历史目标当成当前事实。
2. **能力矩阵**：逐项核对执行环境、权限、工具、依赖解析、网络、数据库边界、生成物来源和副作用。
3. **证据路径**：每一项完成标准必须对应当前允许环境中可实际执行的检查、命令或人工观察。
4. **最小探路验证**：对最高风险链路先做安全、最小的可行性验证，例如依赖解析、最小编译、接口语义或生成链路验证；数据库写入必须遵守根 `AGENTS.md` 第 8.0 节，未获项目负责人明确授权或未确认隔离目标时禁止执行。
5. **同步地图**：明确行为变化需要同步的代码、测试、契约、生成物和当前状态文档，以及历史记录的独立存放位置。
6. **反方审查**：主动寻找最可能导致任务无法完成、假通过或重复返工的条件，并给出处理方式。
7. **等待与升级预算**：为网络、依赖、编译、测试、启动和外部工具链写明进度信号、停止条件、最大重试次数、安全替代路径及需要项目负责人介入时的精确动作，并遵守根 `AGENTS.md` 第 2.2.1 节。

出现以下任一情况，任务不得开始实现：

- 完成依赖被禁止的操作或当前不存在的权限；
- 标准依赖解析、构建或关键工具链尚未证明可用；
- 要求提交生成物，却没有安全、可复现的生成路径；
- 完成标准只能写“应该可行”，没有可执行证据；
- 关键工具链没有等待停止条件、重试上限、安全替代路径评估或人工介入路径；
- 当前环境只能完成实现、不能完成最终集成验证，却没有把两者拆成不同状态和责任。

无法在当前环境完成最终验证时，只拆分“当前实现闭环”和“外部发布验证”两个状态，并明确唯一交接点、负责人和证据；不得继续拆成多个任务层级，也不能把不可执行条件交给主责角色兜底。

## 4. Gate 1：主责执行审查（仅 L2）

主责执行者在大范围修改前必须：

1. 读取本协议、当前任务的紧凑基线或必要任务记录，以及任务关联的权威材料，不以历史对话记忆代替文件；
2. 复核任务范围、权限和每项完成标准的证据路径；
3. 尽早执行安全的依赖解析和最小编译或等价探路检查；
4. 发现完成标准不可执行、材料冲突或验证链路缺失时，立即携带证据退回本次任务主责；涉及需求、总体架构、模板边界或治理权责时再提交总设计师，不得先实现再暴露问题；
5. 确认代码、测试、契约、生成物和文档分别由谁维护，避免平行事实源；
6. 对长操作确认进度信号和停止条件；达到停止条件或关键链路被阻塞时立即报告，禁止重复同一失败路径，并说明需要的人工介入和仍可继续的独立工作。同一对话、同一主责角色不得制造接收回执。

执行审查不是重新设计产品。局部实现可以由主责执行者判断；影响总体范围、公共契约、数据模型或验收标准的冲突必须提交总设计师收敛。

## 5. Gate 2：实现闭环（L1/L2）

实现必须形成一组最小但完整的连贯变更：

- 代码行为变化时，同步相关测试、契约与当前状态文档；
- 生成物必须由可复现流程产生，并被真实构建、测试或业务链路消费，不能只提交一个孤立文件；
- 新增工程骨架、依赖或配置后立即进行最小编译或等价检查，不能积累到最后统一发现；
- 正常路径与失败路径都必须可观察；关键漂移必须有拒绝或失败验证；
- 失败测试必须锁定目标规则的可观察结果；当同一输入可能被多条规则拒绝时，只断言“抛异常”或通用错误码不能证明指定规则生效；
- 承担验收语义的测试样本必须机械证明自身属性，例如固定来源与哈希、帧数、尺寸或损坏位置，不能只凭测试名称和说明文字认定；
- 文档开头描述当前真实状态，历史过程只放在明确标记的历史章节或证据文件中。

## 6. Gate 3：实现者自审（L1/L2）

实现完成后，主责角色必须脱离自己的实现叙述，重新从完成标准开始检查。L1/L2 都只执行与本次风险直接相关的条目；L2 不能借“完整清单”重复无关验证：

1. 在安全且可复现的环境中重新执行适用的依赖解析、编译、测试和生成检查；
2. 同时验证正常路径和至少一个关键失败路径，例如契约漂移确实被拒绝；
   失败路径必须断言目标机制特有的结果，例如精确错误语义、状态变化、调用边界或样本属性，避免由其他拒绝路径造成假绿；
3. 对照权威来源检查实现、测试、生成物、接口契约和文档是否表达同一事实；
4. 搜索已过期措辞、旧状态和“当前事实写在历史记录里”的问题；
5. 确认生成物确实进入消费链路，权限和根 `AGENTS.md` 第 8.0 节数据库执行边界没有被绕过；
6. 发现问题后先修正，再重跑受影响的局部验证；只有公共源、构建链或有状态数据可能受影响时才重跑完整清单。

主责角色必须附带实际执行的证据、未执行项及原因。L1 自审和一次差异复核通过即可完成；L2 若机制特异性自动化和主责自审已经充分覆盖风险，也可由任务主责直接汇总结论，只有第 7 节触发时才增加独立复核。

## 7. Gate 4：条件性最高风险独立复核（仅适用的 L2）

L2 不自动增加独立角色。只有机制特异性自动化不足以证明关键语义、职责隔离是明确要求，或主责角色没有权限取得最高风险证据时，才增加一次独立复核。功能、质量与安全证据由适格的功能回归主责复核，但这不是固定角色节点；需求、总体架构、模板边界和治理决定按独立项目审议机制触发；正式版本整体复盘由独立项目审议者进行。

触发后，独立复核者只复核本次最高风险及验收语义，不重复主责角色的全部验证。复核者必须：

1. 逐项追溯任务目标、变更和证据，确认没有靠修改验收口径取得通过；
2. 独立复现最高风险检查和关键失败路径；
   对多重失败条件的样本必须确认实际触发的是待验收规则，不能仅以最终失败作为通过依据；
3. 检查权限、副作用和根 `AGENTS.md` 第 8.0 节数据库执行边界；
4. 检查与最高风险直接相关的当前文档和实现状态是否一致；
5. 对未执行验证明确影响，不把部分闭环标记为完整完成；
6. 最高风险阻塞项关闭后，由本次任务主责汇总结论并通知项目负责人；复核者不重复生成第二份完整报告。

## 8. 反馈闭环

同类问题第二次出现，或一次问题暴露出系统性缺口时，总设计师先判断是“已有规则未执行”还是“确实缺少机制”。已有规则足以覆盖时只纠正执行，不再新增文档；只有新机制能够机械阻断复发并降低后续成本时，才选择一种长期修正：

- 稳定判断规则更新到本协议；
- 固定信息字段更新到任务模板；
- 角色责任缺口更新到对应角色文档；
- 可以机械判定的规则落为脚本或 CI，并由文档指向该实现；
- 仍需人的语义判断则保留为人工门禁，不夸大自动化能力。

规则只能有一个权威来源。其他文档应引用本协议，不得复制后形成多个版本。

## 9. 历史高风险规则（按任务风险加载）

以下规则来自 V01-05 的多轮返工与 V01-06 的验收假绿风险。只加载与当前任务风险直接相关的条目，L0/L1 不为无关历史问题增加检查：

1. 生成物不得依赖会触发被禁止副作用的应用启动路径；数据库不可用时，契约生成仍须有安全路径，或任务必须明确标为外部验证。
2. 引入或调整依赖前必须先证明标准依赖解析可行，不能把工具链问题留到完整实现之后。
3. 新工程骨架必须尽早最小编译，禁止一次堆叠大量代码后才发现基础结构不成立。
4. 生成物必须进入真实消费链路；“文件存在”不等于能力已经落地。
5. 当前状态与历史记录必须分开；验收优先检查当前真相，不用历史措辞掩盖现状。
6. L2 的主责自我复盘是任务结论的前置证据；第 7 节条件成立时，它也是最高风险独立复核的输入。L0/L1 按第 2 节直接闭环。
7. 总设计师对任务本身是否可执行负责；不可执行的任务不能通过要求研发多改几轮来补救。
8. 安全阈值、权限边界、契约漂移等规则必须由机制特异性断言证明；通用异常、通用状态码或“结果失败”不足以证明目标规则存在。
9. 截断、损坏等同时包含多种失败条件的样本，不能单独证明尺寸、像素、帧数等另一条规则；必须断言精确原因、直接机械核验样本属性，或使用只违反目标规则的有效样本。
10. 外部固定样本必须记录来源、不可变版本和校验值；当样本语义属于验收条件时，自动化测试还必须校验相应哈希或结构属性，防止样本漂移后测试继续假绿。
11. 网络、依赖、编译、测试、启动和外部工具等待必须有界；达到停止条件后按第 2.3 节分类。只有风险阻塞或同一实质路径再次失败才请求人工介入，普通执行错误由当前角色直接修正。
12. `playwright test --list`、静态规格审查和 Mock 网络测试只能证明 E2E 用例存在，不能证明真实浏览器链路可运行。真实 E2E 前必须明确账号状态、权限、一次性数据、导航稳定条件和隔离目录；可能污染状态或产品失败时停止并保留证据，定位器、等待和临时运行器错误按 B 类在原任务内修正，先做局部验证，最终只补一次完整链路。

## 10. 完成清单

### 10.1 L0/L1 紧凑清单

- [ ] 改动没有超出确认范围；
- [ ] 已执行最接近风险的局部验证，未为了形式追加更高层验证；
- [ ] 已检查差异、未执行项和已知风险；
- [ ] 没有新增不必要的角色交接、任务书或证据文档。

### 10.2 L2 完整清单

- [ ] 主责角色已完成最高风险可行性审查，并证明高风险完成标准存在合法证据路径；
- [ ] 长操作已写明进度信号、停止条件、重试上限、安全替代路径和人工介入路径；
- [ ] 主责执行者已完成执行审查和必要的早期探路验证；
- [ ] 代码、测试、契约、生成物和文档形成连贯闭环；
- [ ] 主责执行者已从任务标准重新自审，覆盖正常与关键失败路径；
- [ ] 已判断是否触发条件性独立复核；未触发时有充分机制证据，触发时复核者只复现最高风险证据、没有重复全部验证；
- [ ] 可复用且固化后能降低成本的新教训已进入唯一稳定规则或自动化；已有规则足够时没有重复建文档；
- [ ] 未执行项、外部验证和剩余风险均已明确，不存在口头“应该通过”。

## 11. 跨对话协作与回报（仅真实交接）

只有真实多角色文件所有权、外部验证权限或不可逆授权交接存在时才执行以下规则。L2 标签本身不能触发跨对话；所有等级默认单角色闭环：

1. 只写一份紧凑所有权与交接记录，列明主责对话、必要协作者、可修改文件、禁止文件和唯一回传点，不为每个角色建立平行任务书。
2. 同一对话或同一主责角色不发送“已接收”回执；只有跨对话接收真实文件所有权或外部验证责任时，接收方发送一次简短确认。
3. 执行中出现范围冲突、不可执行标准、需要修改公共文件或 D 类风险阻塞时，必须立即向总设计师对话发送阻塞消息；A/B/C 类按第 2.3 节由原主责角色处理。
4. 完成后只发送一次简短回报，包含结论、最终证据、实际验证、未执行项、风险和文件范围；失败过程压缩进最终回报，不逐轮建立长期记录。
5. 如果当前对话没有跨对话消息工具，必须如实说明并由项目负责人转达；仅因缺少消息工具不得新建证据文件或第二套任务状态。
6. 总设计师是跨对话调度中心。研发对话不得直接改变另一研发任务的范围、状态和文件所有权。
7. 共享工作区的构建产物同样属于共享资源。并行期间禁止执行会删除公共构建产物的 `clean`；需要全量清理或跨任务集成验证时，由总设计师在两个任务源文件冻结后统一执行。

跨对话消息可按需要参考以下格式；简单交接只写结论、责任和唯一回传点，不要求填满全部字段：

```text
[任务ID][接收/阻塞/申请验收]
当前结论：...
证据文件：...
已执行验证：...
未执行项/风险：...
需要总设计师处理：...
```
