# 项目愿景：AI 可装配、人可审计的全栈模板

> 状态：已确认
> 版本：0.3
> 确认日期：2026-08-12（项目负责人再次确认模板优先于参考项目）
> 适用范围：全项目（架构、需求、AI 协作、素材库共同遵循）
> 关联材料：无

## 1. 一句话定位

`internal-admin-template` 是**内部管理系统领域的"Spring Boot"**：架构决策由人提前固化在模板中，AI 在既定约束内完成装配，让独立开发者和企业团队都能像使用成熟框架一样快速、一致地搭建系统。

它不是"AI 全量生成系统的脚手架"，而是**全面辅助**的开发模板——AI 负责高质量填充，人负责架构决策与产物验收。

### 1.1 优先级

本仓库按以下顺序作出取舍：

1. **模板核心**：启动体验、基础架构、通用能力、裁剪边界和质量入口；
2. **派生机制**：如何从模板创建项目、引入/移除模块并保持升级可理解；
3. **参考实现**：用真实业务闭环证明模板可用；
4. **参考业务扩展**：只在继续验证模板能力时增加，不以把示例做成完整产品为目标。

当模板复用价值与参考项目功能发生冲突时，模板优先。参考实现不得把业务专用模型、路由、权限或界面假设下沉为模板核心的强制前提。

## 2. 目标与边界

### 2.1 全面辅助，而非全量生成

- **人 = 架构师**：确定模块边界、数据模型、权限模型、视觉方向，审批需求与产物；
- **AI = 装配工**：在模板约束内完成需求 → 表结构 → Liquibase → 后端 → OpenAPI → 前端 → 测试的装配；
- 每条 AI 产物必须通过**自动化质量门禁 + 人工审查**两个关卡，任何一步未过即停止，不允许猜测或兜底继续。

### 2.2 批量生产两种形态（都支持）

1. **模板派生独立系统**：从一个模板派生出多个相似的独立系统（进销存、资产管理、CRM 等），每个都是独立项目，类似 Spring Initializr 依据依赖选择生成新项目；
2. **系统内模块组合**：在同一个系统内按需引入模块（用户/内容/文件/审计…），AI 把新需求装配成新模块，并遵守模块组合契约。

### 2.3 分层设计：独立开发者与企业团队兼顾

| 层 | 服务对象 | 特征 |
| --- | --- | --- |
| L1 核心模板 | 独立开发者 | 上手简单：README 即可启动、默认零配置、AI 辅助度高、约束以必要为限 |
| L2 企业增强 | 中小企业团队 | 作为可选增强层：审计追溯、模块可裁剪、权限与测试的严格门禁、派生记录 |

L1 是模板的基础，L2 不改变 L1 的结构，只在其上增加纪律。禁止因为企业级要求而抬高独立开发者的上手门槛。

## 3. 核心设计：模块化 AI 能力包

每个业务模块都是一个**完整自洽、可独立引入的能力包**，这是"批量生产"保持一致性、又允许自由组合的基础。

### 3.1 每个模块必须自带（缺一不可）

- **AI 提示词**：该模块的 AI 开发提示（实现指引、边界、禁止事项），供 AI 在模块内开发时加载；
- **设计文档**：模块职责、边界、公开 API 契约、与其他模块的组合方式；
- **数据契约**：表结构方案、Liquibase 变更集、DO/DTO；
- **实现资产**：后端代码、前端页面与组件、测试；
- **视觉基线与素材状态**：使用项目现有设计令牌和组件保持一致；外部素材必须先完成登记与批准，禁止把未登记素材描述为已批准资产。

### 3.2 组合规则

- 模块可**单独引入**（只取需要的模块，类似 Spring Starters）；
- 模块可**整体组合**（多个模块构成完整系统）；
- 组合必须遵守已确认的依赖方向（`app-server → 业务模块 → 基础模块`）、跨模块只走公开 API 或本地事件、禁止跨模块访问内部 Mapper/DO；
- 模块组合方式必须随模块设计文档一起提供，不允许出现"单独引入能跑、组合后冲突"的隐性耦合。

## 4. AI 幻觉与不一致治理（四条防线）

多模块大型系统中 AI 的幻觉和偏差，靠以下四条防线系统性解决：

### 防线一：规范约束

AGENTS.md 是 AI 行为宪法：范围控制、失败可见、最小连贯改动、Javadoc 规则。需求按状态分级，只有"已确认"可作为实现依据，"草稿"和"待确认"禁止实现。

### 防线二：契约固化

单一事实来源，杜绝命名与模型漂移：

- 数据对象只使用 DO/DTO；
- 权限模型、模块边界、依赖方向固定；
- 项目现有 `tokens.css` 是当前视觉令牌的唯一实现来源，禁止并行创建第二套变量；该代码事实不等同于已经完成素材登记与批准。
- 依赖版本统一锁定（BOM 式管理）。

### 防线三：素材来源可追溯（尚未完成工程证明）

目标机制是：AI 只能使用已登记并批准的外部素材（组件、令牌、配方及许可证归档），禁止为了图方便现编组件、现造配色或猜测许可证。当前仓库尚无已登记外部素材，也没有 `02-已批准` 或 `admin-ui-kit-v0.1` 的可核验批准记录，因此本防线不能宣称已经落地。建立真实登记前，只能复用项目现有代码中的组件和 `tokens.css`，不得把它们扩张解释为已批准素材包。

### 防线四：自动化质量门禁 + 人工审查

质量门禁必须是可执行命令，至少覆盖：编译、测试、类型检查、Liquibase 从空库迁移、Javadoc 链接、模块依赖方向、前后端契约一致性、越界修改检查。门禁未过，AI 产物不得视为完成。

## 5. 与现有资产的关系

| 资产 | 在本愿景中的角色 |
| --- | --- |
| `AGENTS.md` | 防线一：AI 行为宪法，需随本愿景补充"装配规则"（引用素材库、锁定版本、模块提示词加载） |
| `requirements/` | 需求状态分级与验收标准，AI 装配的输入 |
| `frontend/src/shared/styles/tokens.css` 与现有组件 | 当前可核验的视觉实现基线，不代表已经形成独立素材包或批准记录 |
| `references/README.md` | 外部材料登记入口；当前登记为空，防线三仍待真实素材验证 |
| `docs/architecture/` | 模块边界、认证、前端结构的已确认基线 |
| 早期规划与工作模式记录 | 仅作为形成过程；本文件是已确认的愿景基线，冲突时以本文件为准 |

## 6. 演进路线（与 0.1 的关系）

1. **工程骨架**：创建可运行的 backend（Maven 多模块）+ frontend（Vue），让模板有血肉（0.1 范围）；
2. **首个闭环模块**：用"公开主页内容发布"闭环验证能力包的代码、设计、契约和测试形态；外部素材登记与批准尚未完成工程证明；
3. **模块提示词沉淀**：从首个模块提炼 AI 提示词模板，形成"新增模块 = 复制能力包模板"的派生机制；
4. **质量门禁工具化**：把 0.1 质量门禁变成可执行命令，本地与 CI 一致；
5. **派生文档**：输出"从模板派生独立系统 / 在系统内新增模块"的操作说明与改动记录规范。

0.1 已完成工程骨架、模块形态、提示词模板和质量门禁的首轮工程证明；外部素材登记与批准不在已证明范围内。下一阶段首先完成第 5 项，并实际验证：从干净模板派生新项目、替换项目身份信息、移除参考 `site` 模块后仍可构建运行，以及用第二个小业务模块复用能力包流程。上述模板能力未验证前，不优先扩展公开主页功能。

0.1 的业务范围仍以 `requirements/V0_1_SCOPE.md` 为准，本文件不扩大 0.1 功能范围，只确认项目的长期目标和 AI 协作方式。

## 7. 明确不追求

- 不追求 AI 全量自动生成系统（幻觉风险不可审计，不是目标）；
- 不做低代码/可视化拖拽平台；
- 不为"以后可能用"预建空模块、空提示词和占位能力包；
- 不因企业级增强层抬高独立开发者的启动门槛。
