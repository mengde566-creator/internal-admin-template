## 2. 门禁依据

### 2.1 干净环境启动：通过

`V01-12_FULL_VALIDATION_REPORT.md` 已对主模板固定 SHA
`90d4d313b3483f07237a6e0cf342953d980f20f5` 证明：

- 干净 worktree 与锁定依赖安装成功；
- `quality.sh --database` 通过，Liquibase `Run=16 / Total=16`；
- `dev.sh start/status/stop` 生命周期通过；
- Chromium 真实链路 3/3 通过；
- GitHub Actions 对同一 SHA 运行成功。

该证据证明主模板可从干净来源运行，不证明派生项目已经完成同等级运行验证。

### 2.2 项目身份替换：部分通过

派生项目已真实替换：

- Maven 根构件与所有子模块父构件；
- 前端包名与锁文件身份；
- Spring 应用名、管理端品牌和页面标题；
- 默认 SQLite 文件名；
- README、当前产品愿景、需求入口与架构现势。

派生项目保留 `com.internaladmin` Java 包名。这是为了避免约 120 个文件的机械改包和后续
上游冲突，不是遗漏；但主模板仍缺少一份正式规则说明哪些身份必须替换、哪些内部标识可以
保留。因此当前证明的是“能够人工完成一次受控替换”，不是“模板已提供稳定改名机制”。

### 2.3 移除参考 `site` 业务：部分通过

派生提交 `0bc11be` 已真实删除或解除以下装配：

- 后端 `module-site`、Maven reactor、`app-server` 依赖和 Mapper 扫描；
- `site` Liquibase include；
- 前端 `modules/site`、公开/管理路由、导航、E2E 与 Playwright 配置；
- OpenAPI 路径、生成类型、契约断言、`SiteFlowTest` 和公开站点冒烟脚本；
- Security 中仅服务于公开站点的 `/api/public/**` 放行。

裁剪后实际通过一次最终无数据库质量门禁：会话安全 3/3、文件存储 12/12、OpenAPI 2/2、
Vitest 5/5、TypeScript 和前端构建全部通过。

本次还暴露两处模板耦合：

1. 通用 `module-file` 使用 `site:homepage:edit` 权限，派生项目临时改为 `file:manage`；
2. 会话安全测试通过 `/api/public/session-bootstrap` 依赖公开路径，收紧安全规则后首次返回 401，
   派生项目只将测试端点移动到既有公开登录路径，一次修正后门禁通过。

尚未执行派生项目的隔离 SQLite、Liquibase、服务生命周期和真实页面验证，因此裁剪门禁只能
判为工程层部分通过。模板自身也尚未提供模块注册清单或自动裁剪工具。

### 2.4 用能力包装配新业务模块：未通过

本次派生的目标是验证改名和删除参考业务，没有新增设备表、接口、页面或能力包。派生项目是
长期保留的验证样本，不是新的产品开发主线；不能为了让审计表格变绿而自动开发“设备台账”。

只有主模板未来确实需要验证第二次装配，且项目负责人明确确认一个最小业务样本时，才执行该
门禁。当前能力包结构存在，但可重复装配仍缺少真实证据。

## 3. 成熟度判定

当前定位更新为：

> **具备一次真实手工派生和参考业务裁剪证据的内部管理模板；尚未达到可稳定、低成本持续派生的成熟模板。**

相较首次静态审计，成熟度已经提高；剩余问题也从“是否能做”收敛为“模板是否提供短小、
可重复、可升级的正式路径”。

## 4. 主线后续事项

回归 `internal-admin-template` 主线后，只处理本次派生直接证明的模板问题：

1. 确认并处理 `module-file` 对 `site` 专属权限的耦合；
2. 提供一份短小派生说明，列出必须替换身份、允许保留标识、`site` 裁剪装配点和最低验证；
3. 在下一次主模板真实升级时，用现有派生项目验证一次 `upstream` 同步和冲突成本；
4. 派生项目需要完整交付时，再单独运行其隔离数据库、服务生命周期和页面验证；当前审计不以此阻塞主线；
5. 第二业务模块保持未验证，不自动转化为设备系统开发计划。

上述事项不得合并成新的大型“模板成熟度工程”。每次只处理一个闭环，使用与风险最近的证据。

## 5. 流程试验结论

本次派生的执行方式比 0.1 封版明显轻：没有任务书、实施报告、多轮 E2E 或数据库验证；一次
依赖恢复、一次测试修正后，最终无数据库门禁约 14 秒通过。

但生产方法只能判为**部分通过**：总设计师越过研发角色亲自完成 85 个文件的派生改动，且完成
后错误地把长期验证样本延伸为设备产品开发路线。角色路由规则已经在主模板工作区修正并经独立
项目审议者复核，但仍需由后续真实任务证明执行有效。

## 6. 本次审计边界

本次更新只读取主模板原审计、派生提交与派生记录，没有修改生产代码、派生项目或任务状态，
没有运行 Maven、npm、数据库、服务或 E2E。派生项目的无数据库结果来自其已完成并提交的
真实执行记录；完整运行仍明确标为未验证。
