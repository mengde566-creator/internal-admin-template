# 需求索引与治理规则

> 状态：生效  
> 版本：0.1  
> 更新日期：2026-07-18

`requirements/` 只描述系统需要解决什么问题、提供什么行为以及如何验收，不在这里规定具体类名、SQL 写法或页面组件实现。

## 1. 权威级别

发生冲突时按以下顺序处理：

1. 用户在当前任务中的明确要求；
2. 状态为“已确认”的需求文档；
3. 已生效的架构决策和开发规范；
4. 状态为“草稿”或“待确认”的需求文档；
5. `references/` 中的参考材料。

参考材料不是需求。AI 不得因为截图、竞品或外部文档中存在某个功能，就自行把该功能加入产品范围。

## 2. 需求状态

需求文档只使用以下状态：

| 状态 | 含义 | 是否允许实现 |
| --- | --- | --- |
| 草稿 | 正在分析，内容可能变化 | 否 |
| 待确认 | 已形成候选方案，等待明确选择 | 否 |
| 已确认 | 范围和验收条件已经确认 | 是 |
| 已废弃 | 不再适用，仅保留历史说明 | 否 |

禁止把沉默、未回复或没有反对解释为“已确认”。需求状态只能由用户明确决定。

## 4. 文档头信息

每份需求文档必须在标题后包含：

```markdown
> 状态：草稿 | 待确认 | 已确认 | 已废弃
> 版本：0.1
> 适用模块：模块名称或“全项目”
> 关联前端：相关目录；未建立时写“待建立”
> 关联后端：相关 Maven 模块；未建立时写“待建立”
> 关联材料：材料路径；没有时写“无”
```

## 5. 单项需求格式

可实现的需求至少包含：

```markdown
### REQ-模块-编号：简短名称

- 状态：待确认
- 使用者：谁会使用
- 前置条件：开始前必须满足什么
- 触发：什么动作或事件开始该行为
- 主流程：正常情况下按顺序发生什么
- 异常流程：哪些情况必须明确失败
- 权限：谁能执行、能访问哪些数据
- 数据：读取、创建或修改什么
- 验收标准：如何证明需求完成
- 非目标：本需求明确不处理什么
```

主流程和异常流程必须可验证，禁止使用“适当处理”“智能判断”“尽量兼容”等无法验收的描述。

## 6. 变更流程

1. 新想法先进入草稿，不直接进入实现。
2. 补齐角色、流程、权限、数据和验收标准后进入待确认。
3. 用户明确确认后才改为已确认。
4. 实现发现需求缺口时回到需求讨论，禁止由代码兜底替代需求决定。
5. 已确认需求发生变化时，必须更新版本和变更说明，并检查前后端、数据库和测试影响。

## 7. AI 读取规则

- 所有任务先读取本索引。
- 只读取与当前任务相关的需求文档，不一次加载全部需求。
- 开始实现前必须在对话中列出实际读取的需求文件及其状态。
- 草稿可以提出建议，但不能被实现成默认行为。
- 材料只有被需求文档关联或用户明确指定时才读取。
