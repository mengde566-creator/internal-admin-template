# 多端文件测试一致性

文件功能的后端、前端、真实浏览器和人工验收必须使用同一个可追溯的样本族。任一层通过只证明该层通过，不能代替下一层。

## 先固定样本身份

- 以当前生产代码或页面实际提供的标准模板为唯一源头；禁止仿造表头或另建“看起来一样”的工作簿。
- 正常、异常和空文件样本都必须从同一份标准模板派生，保留同样的工作表、表头、格式和模板元数据。
- 可以为不同场景使用不同业务数据，但必须记录共同模板来源、统一生成方式、场景标识、预期结果和每个文件的 SHA-256。
- 同一个跨端验收场景优先在所有层使用字节完全相同的文件。如必须复制，复制前后 SHA-256 必须一致。
- 文件一旦进入验证链就不得重新生成、替换或就地修改。任一变更都产生新样本身份，原跨端证据不得继续沿用。

XLSX/DOCX/PPTX 等 OOXML 样本必须通过 Excel、Apache POI、openpyxl 或项目已批准的文档库正常编辑和保存。禁止用字符串拼接或直接改 ZIP/XML 内部文件的方式制作验收样本。

## 统一场景定义

- **正常样本**：从正式模板派生，填入完整有效的最小业务数据，用于证明成功路径和最终可见收益。
- **异常样本**：先生成正常样本，再只改动当前要验证的字段或结构；其他内容保持有效，以便错误能归因到唯一异常。
- **空数据样本**：保留正式模板的表头、工作表和格式，不填业务数据行。它与“零字节文件”是两个不同场景，不得混用。

异常类型较多时可以建立多个异常样本，但它们必须属于同一模板族，并分别标明唯一预期错误。

## 按层前移验证

1. **文件自检**：记录绝对路径、文件名、大小和 SHA-256；检查容器完整性，并用支持该格式的正常库读出关键内容。这只证明样本本身可读。
2. **后端固定样本测试**：直接加载固定 fixture 原始字节，先断言 SHA-256，再经过项目实际文件安全校验、存储/读取、解析和业务分类。可隔离 Mapper 和外部服务，但禁止绕开生产解析器后伪造解析结果。
3. **前端自动测试**：选择同一 fixture 或其字节相同副本，断言选中文件身份、上传请求和用户可见状态。Mock 接口只能证明前端交互，不得冒充后端文件解析成功。
4. **真实浏览器**：先确认运行中后端包含已验证代码，然后仅上传已经前三层确认的固定文件。断言页面中的文件名、业务分类、错误位置/原因、确认动作和最终业务结果。
5. **人工验收**：将同一文件放在项目负责人可访问的稳定位置，提供文件名、SHA-256、关键内容和预期结果；在进入最终写操作前明确请其确认文件正确。

前一层未通过时不得进入后一层。真实浏览器不是文件生成器、后端调试器或运行版本检测器。

## 证据一致性

一条跨端结论至少要能回答：

- 它使用哪个模板生成？
- 它属于正常、哪一种异常，还是空数据场景？
- 后端、前端、浏览器和人工使用的文件 SHA-256 是什么？
- 每层实际经过了哪些生产代码边界，断言了什么可见结果？
- 浏览器连接的运行包是否新于相关源码？

这些内容优先保存在测试名、fixture 目录、断言和交付回报中，不为普通任务另建多份机械报告。

## 先建立可观察的阶段边界

异步上传、文件安全校验、存储/读取、解析、业务分类和结果持久化组成复杂链路时，生产实现必须在阶段边界留下正式诊断日志，不得等失败后靠临时打印猜测。

- 用作业标识、修订号和受控资产标识串起同一次处理；记录阶段、格式、字节数、行数、分类计数、耗时和稳定错误码。
- 表头诊断只记录项目规范字段到列号的映射，不记录用户原始表头、文件正文、完整单元格、内部路径、凭据、完整文件指纹或异常堆栈。
- 同一异常只在合适边界记录一次；日志不得改变原失败行为，也不得成为捕获异常后继续执行的理由。
- 测试或复核至少确认成功终态和一个失败终态能被定位，并确认日志未出现 fixture 中的业务值。

这些日志用于确定首个发生偏差的阶段，不代替固定样本测试、真实浏览器结果或人工验收。

## 失败分层与止损

- 样本内容或指纹不一致：停在样本层，不改业务代码。
- 后端固定样本失败：按安全校验、存储/读取、解析、分类定位，不进入前端。
- 后端通过而前端失败：先核对文件指纹、文件选择/传输、请求和运行版本，不重写后端解析器。
- 自动化工具无权选择本地文件：标记为测试工具链阻塞，不得归因为产品上传失败。
- 真实产品结果不符：保留当次文件和时间线，停止点击、换文件和堆补丁，回到首个发生偏差的层复盘。

同一主链两次未得到同一样本身份的完整证据，或任意一次替换样本后沿用旧结论，立即停止重试并进入分层复盘。
